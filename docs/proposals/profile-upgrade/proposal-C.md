# طرح C — پروندهٔ ناشر: از مصرف‌کنندهٔ داده تا امضای خروجی

> پایه: docs/PROFILE-FLOW-MAP.md (نسخهٔ ۱.۲۷.۴۹، کامل خوانده شد) و قرارداد گزارش‌ساز. **هشدار صادقانه**: `docs/REPORT-DESIGN.md` در مخزن موجود نیست (فقط ارجاع معلق در PROFILE-FLOW-MAP.md خط ۳ و ۵۰)؛ شماره‌گذاری G1..G7 و قرارداد `ReportSection` در این طرح از موتورهای واقعی موجود بازسازی شده‌اند و هر نام، به مسیر کد لنگر شده تا با فرود سند اصلی فقط جای‌گزین نام لازم باشد، نه بازنویسی سیم‌کشی.

## ۱. تشخیص — پنج ضعف با شاهد

1. **تنها «گزارش» خروجی پرونده، متن آزاد است نه سند ساخت‌یافته**: `openTeacherReportModal` (student-profile.js:961-997) فقط یک textarea دارد و به `POST /api/notifications/teacher-report` (خط ۹۸۶؛ مسیر سرور در src/application/notify/routes.ts:149) می‌فرستد. هیچ پیوندی به موتورهای گزارش (progress-report.js، clinical-engine/report.ts) ندارد و چیزی برای آرشیو/استناد باقی نمی‌ماند.
2. **موتورهای گزارش read-only و بی‌نسخه‌اند**: سربرگ report.ts خط ۳ می‌گوید «گزارش read-only است و هیچ‌جا persist نمی‌شود»؛ progress-report.js تاریخ گزارش را در هر رندر با `tehranTodayYmd()` می‌سازد (خط ۲۰۴ و ۷۱۲) و پانوشت فقط «تولید خودکار از سامانه» است (خط ۲۹۲-۲۹۵). چاپِ دیروز قابل بازتولید نیست؛ شمارهٔ گزارش، امضا و مهر وجود ندارد.
3. **ردپای گزارش ارسالی، «رویداد» است نه «سند»**: کارت «گزارش‌های ارسالی» (student-profile.js:727-736) فقط می‌گوید در تب تاریخچه به‌صورت رویداد پیام ببینید؛ سرویس خط زمانی هم آن را به `kind:'notification'` نرمال می‌کند (src/application/student-timeline/service.ts:353-360). نسخهٔ واقعاً ارسال‌شده قابل بازیابی نیست.
4. **خروجی‌های چاپی جزیره‌ای‌اند و از پرونده نمی‌آیند**: progress-report.js مستقیماً endpointهای خودش را می‌خواند (خط ۱۴۰-۱۴۷) و ورود به آن از پرونده نیست؛ نقشهٔ جریان §۷.۳ همین را تأیید می‌کند. نتیجه: معنابخشی بخش‌های پرونده کنار هم، فقط در چاپ جزیره‌ای رخ می‌دهد نه از دل پرونده.
5. **تاریخچه رویداد-محور است و جای سند خروجی ندارد**: `TIMELINE_FILTERS` (student-profile.js:35) نه فیلتر «گزارش خروجی» دارد و نه kindی برای سند نسخه‌دار؛ ضعف ۲ و ۳ نقشهٔ جریان (§۸) بی‌پاسخ مانده‌اند.

## ۲. موتور خروجی از پرونده — فلوی انتخاب → پیش‌نمایش → snapshot → چاپ/ارسال

**ورودی‌ها (بدون ساخت موتور تازه):** همان endpointهای موجود — شناسنامه از `/api/students/:id`، چک‌لیست از `ot/progress`+`ot/profile`، بازهٔ مداخله از `/api/clinical-paths/:id/report` (که خودش buildPathwayReport را صدا می‌زند)، رویدادها از `case-events?limit=200`، بازی‌ها از rxPanel، پرسشنامه‌ها از survey-insights. نمای مستقل progress-report باقی می‌ماند و از builder حذف نمی‌شود؛ builder درِ جلوی خروجی می‌شود و نماها همان‌طور که هستند قابل انتخاب‌اند.

**قرارداد ReportSection (پیشنهاد مینیمال برای هم‌سویی، در `src/domain/report-sections/`):**

```ts
interface ReportSection {
  key: string;                                   // 'fx_baseline' | 'pathway_sessions' | ...
  title: string;
  audience: Array<'clinical'|'family'|'school'>; // در کدام نسخه مجاز است
  build(ctx: SectionCtx): Promise<SectionView|null>; // null = صادقانه «ندارم»، نه placeholder
}
```

ساختِ بخش، تابع خالص بدون دسترسی DB است — دقیقاً هم‌الگوی clinical-engine/report.ts (سربرگ خط ۱-۳). فیلتر نسخه (family/school) در **سرور** روی snapshot اعمال می‌شود؛ DSM/مالی با `audience:'clinical'` از نسخهٔ خانواده بیرون می‌ماند (قاعدهٔ حریم §۹ نقشه).

**فلوی چهارقدمی:**

1. **انتخاب**: دکمهٔ «خروجی گزارش» → صفحهٔ خودگردان `#/students/:id/report-builder` (chunk داینامیک، هم‌الگوی import بازی‌ها در student-profile.js:383). انتخاب قالب G1..G7 + بازه + تیک بخش‌ها؛ catalog بخش‌ها از سرور می‌آید (داده‌محور)، بخش‌های خارج از نقش کاربر اصلاً نشان داده نمی‌شوند؛ بخش بدون داده با برچسب «فعلاً خالی — حذف از خروجی» پیش‌فرضِ بسته می‌شود.
2. **پیش‌نمایش**: همان قالب چاپ موجود (`pr-sheet`/`pr-head`/`pr-kpis`/`pr-table`/`pr-foot` + `print-hide`) — بدون CSS تازه؛ کف فونت ۱۲px گیت موجود را پاس می‌کند.
3. **قطعی‌سازی (snapshot)**: `POST /api/students/:id/report-snapshots` → سرور همهٔ بخش‌ها را می‌سازد، JSON نهایی + SHA-256 محتوا را در جدول تازهٔ `report_snapshots` ذخیره می‌کند، **شمارهٔ گزارش صادر می‌کند** (ترتیب مرکزی سال-شماره، از جدول شمارنده)، امضاکنندهٔ ثبت‌شده (نام/نقش در لحظهٔ قطعی‌سازی) و تاریخ قطعی را مهر می‌زند. بلوک امضا/مهر در `pr-foot`: نام متخصص، شمارهٔ گزارش، کد راستی‌آزمایی کوتاه (صفحهٔ عمومی verify با شماره+کد)، سربرگ مرکز همان `pr-head__brand` موجود است (progress-report.js:194).
4. **چاپ/ارسال**: پس از قطعی‌سازی، پیش‌نمایش **از snapshot** رندر می‌شود نه دادهٔ زنده — چیزی که چاپ شد همان چیزی است که آرشیو شد. **شکل رکورد `report_snapshots` (پیشنهاد):**

```
id · student_id · template_key (G1..G7) · period_from/to
sections_json (بخش‌های قطعی‌شده با دادهٔ نهایی) · content_hash (SHA-256)
report_no (۱۴۰۵-۰۰۴۷) · version · superseded_by
signed_by (staff_id + نام/نقش در لحظهٔ قطعی‌سازی) · verified_code (کد راستی‌آزمایی)
created_at · created_by_role
```

جدول ارسال جدا است: `report_sends` (snapshot_id · گیرنده/نقش · کانال بله یا توکن · expires_at · revoked_at) — آرشیو با هر بار ارسال تغییر نمی‌کند، فقط سابقهٔ گیرنده‌ها طول می‌کشد.

**شمارهٔ گزارش و راستی‌آزمایی**: شماره از شمارندهٔ سالانهٔ مرکز است (قالب `سال-شماره`، جلالی) تا در اداره/کمیسیون قابل ارجاع باشد؛ کد راستی‌آزمایی کوتاه (۸ نویسه) روی همان ردیف می‌نشیند و صفحهٔ عمومی verify با جفت «شماره + کد» فقط وضعیت (صادرشده/منقضی/ابطال‌شده) و عنوان سند را نشان می‌دهد — محتوای گزارش بدون توکن گیرنده باز نمی‌شود.

صفحهٔ builder چهار حالت دارد: انتخاب قالب/بازه → تیک بخش‌ها → پیش‌نمایش زنده → سند قطعی (پس از ثبت، state قفل می‌شود و هر ویرایش = نسخهٔ جدید با شمارهٔ تازه و ارجاع به نسخهٔ قبلی). چاپ = `window.print()` روی pr-sheet (بالینی) و مسیر بازنویسی‌شدهٔ printVariant برای نسخه‌های دیگر (الگوی progress-report.js:593-607). ارسال امن = پیام کوتاه + لینک توکن‌دار `/#/shared-report/:token` که به **snapshot** اشاره می‌کند نه دادهٔ زنده؛ توکن تصادفی، انقضادار، قابل ابطال؛ گیرنده از همان recipients موجود buildTeacherMessageCard (student-profile.js:1017-1034) و کانال بات بله (هم‌الگوی ارسال‌های فعلی routes.ts:149 و 157).

## ۴. طراحی تاریخچهٔ فعالیت‌ها (شامل آرشیو گزارش‌ها)

- **kind جدید `report_export`** در خط زمانی سرور-محور: جدول `report_snapshots` به‌عنوان جدول دهم تجمیع، نرمال به `{at, kind, title: 'گزارش شمارهٔ …', subtitle: قالب+بازه, actor: امضاکننده, ref: snapshotId}` — دقیقاً هم‌الگوی notification در service.ts:353-360 و merge در student-timeline/pure.ts.
- **فیلتر چیپی تازه** «گزارش‌های خروجی» در TIMELINE_FILTERS (student-profile.js:35، kinds='report_export') — آرشیو گزارش‌ها یعنی خط زمانی، نه صفحهٔ موازی.
- **کارت آرشیو بالای خط زمانی تب تاریخچه**: سه شمارنده (صادرشده/ارسال‌شده/پیوند فعال) + آخرین ۵ گزارش با دکمهٔ «بازکردن نسخهٔ قطعی» (read-only از snapshot)، «چاپ مجدد» و «ارسال با توکن تازه» — گیرندهٔ جدید همان محتوای قبلی را می‌گیرد.
- **معنابخشی کنار هم**: رخدادهای دوره (جلسات، رویدادها، تمرین‌ها) زیر هر آیتم آرشیو قرار می‌گیرند؛ هر گزارش خروجی خودش را به بازهٔ وقوع‌شده قفل می‌کند — تاریخچه از «فهرست رخداد» به «روایت با اسناد دوره» ارتقا می‌یابد (ضعف ۲ نقشه).
- **جریان روزمره**: پس از ثبت گزارش جلسهٔ آخر یک دوره، پیشنهاد action-محور «خروجی این دوره را ببند» (جواب ضعف ۶ نقشه) در تب جلسات؛ یک کلیک تا پیش‌نمایش.
- **دسترسی ردیف‌های آرشیو**: بازکردن نسخهٔ قطعی همان RBAC بخش‌های داخلش را می‌گیرد (کسی که کمیسیون را نمی‌بیند، در نسخهٔ قطعی هم نمی‌بیند)؛ معلم/خانواده فقط از مسیر توکن وارد می‌شوند و در پرونده ردی ندارند.
- **نمونهٔ ردیف تاریخچه**: `۱۴۰۵/۰۸/۱۰ — گزارش شمارهٔ ۱۴۰۵-۰۰۴۷ (G2 · بازهٔ ۰۷/۰۱ تا ۰۸/۱۰) · امضا: دکتر …، درمانگر · ارسال به معلم کلاس ۳ (توکن فعال تا ۰۸/۲۴) · [بازکردن] [چاپ مجدد] [ارسال تازه]`.

## ۵. ساختار تب‌ها با وجود موتور خروجی

- **تب جدید نمی‌سازم.** موتور خروجی یک صفحهٔ خودگردان با route عمیق است که از دو جا باز می‌شود: دکمهٔ «خروجی گزارش» در page-head پرونده (کنار دکمهٔ بازگشت، student-profile.js:284-287) و یک دکمه در کارت «گزارش‌های ارسالی» تب comms (خط ۷۲۷-۷۳۶).
- چرا: تب هشتم، عمق نابرابر تب‌ها را بدتر می‌کند (ضعف ۱ نقشه §۸.۱)؛ مودال از سال‌ها تجربهٔ همین مخزن برای جریان چندقدمی (تیک/پیش‌نمایش) مناسب نیست — progress-report هم امروز نمای جدا با مسیر از پرونده است (خط ۱۷۶-۱۷۷ «بازگشت به پروفایل»).
- **تقسیم مسئولیت**: builder = ساخت و قطعی‌سازی؛ تاریخچه = آرشیو (فیلتر report_export)؛ comms = گیرنده‌ها و کانال‌ها. مودال متن آزاد فعلی به «پیام آزاد به معلم» تغییر نام می‌یابد تا با گزارش ساخت‌یافته اشتباه نشود.
- **قرارداد بازسازی بی‌صدا حفظ می‌شود**: فقط `onReportSnapshotSent` به نقشهٔ mutation اضافه می‌شود که `rerenderTabIf(['timeline','comms'])` را صدا می‌زند (هم‌الگوی onBaleSent خط ۳۷۳)؛ بقیهٔ نقشهٔ دستی خطوط ۳۶۶-۳۷۳ دست نمی‌خورد.
- **دیزلینک‌ها**: `#/students/:id/report-builder` (صفحهٔ ساخت)، `#/students/:id/report-builder?snapshot=:sid` (نسخهٔ قطعی — هم‌الگوی deep-link `?pathway=` در progress-report.js:118)، `#/students/:id?tab=timeline&filter=reports` (آرشیو) — سه ورودی مستقل، بدون وابستگی به تب فعال.
- **بارگیری سبک**: builder فقط هنگام ورود به آن route با import داینامیک بالا می‌آید (هم‌الگوی games-console در خط ۳۸۱-۳۹۰)؛ به هزینهٔ ~۱۰ endpoint ورود اول پرونده (ضعف ۴ نقشه) چیزی اضافه نمی‌کند.

## ۶. امواج پیاده‌سازی

**موج ۱ — ستون فقرات نسخه‌دار** (پرونده→گزارش):
جدول `report_snapshots` + شمارندهٔ شمارهٔ گزارش + endpointهای snapshot + builder با G1 و G2 (موتورهای موجود) + چاپ از snapshot + kind `report_export` در خط زمانی. *گیت پذیرش*: بازکردن نسخهٔ قطعی عین محتوای هش‌شده را بازتولید کند؛ چاپ A4 با tokens موجود و کف فونت ۱۲px؛ tsc/vitest سبز.

**موج ۲ — نسخه‌ها و ارسال امن**:
فیلتر audience روی snapshot (متخصص/والد/مدرسه از یک سند) + ارسال توکن‌دار بله + صفحهٔ راستی‌آزمایی عمومی (شماره+کد) + ابطال توکن. *گیت پذیرش*: تست RBAC — توکن والد به DSM/مالی/کمیسیون نمی‌رسد؛ توکن منقضی/ابطال‌شده 404 می‌دهد؛ هر ارسال در audit append-only ثبت می‌شود.

**موج ۳ — پوشش کامل و جریان روزمره**:
G3..G7 و باقی بخش‌ها + فیلتر چیپی + پیشنهاد «بستن دوره» + تغییر نام مودال متن آزاد + پیوست مدارک. *گیت پذیرش*: هر بخش یا دادهٔ زنده دارد یا صادقانه حذف می‌شود (بدون placeholder — قاعدهٔ §۹ نقشه)؛ نقشهٔ rerender بدون رگرسیون.

**دامنهٔ فایل‌ها در هر موج (تا ریسک فایل ۱۴۳۳خطی کنترل بماند):**
- موج ۱: `src/domain/report-sections/` (جدید) · migration جدول snapshot · `src/application/report-export/` (جدید: routes/service) · `public/assets/js/report-builder.js` (chunk جدید) · افزودن kind به `src/application/student-timeline/` · در student-profile.js فقط دکمهٔ page-head + یک mutation تازه.
- موج ۲: فیلتر audience در سرور + `report_sends` + توکن/shared-report route + صفحهٔ verify عمومی (بدون نشست).
- موج ۳: بخش‌های G3..G7 (داخل report-sections) + TIMELINE_FILTERS + rename مودال در student-profile.js.

## ۸. پنج تفاوت اصلی طرح من

1. **قطعی‌سازی قبل از ارسال**: هر خروجی، سند نسخه‌دار با شمارهٔ مرکزی و امضاست و چاپ/ارسال فقط از snapshot انجام می‌شود — «چاپ دیروز» قابل بازتولید و استناد است؛ امروز هیچ‌کدام از موتورها persist نمی‌کنند (report.ts:۳).
2. **سه نسخه از یک سند قطعی، نه سه گزارش جدا**: نسخهٔ متخصص/والد/مدرسه فیلتر audience روی همان snapshot است؛ امتداد سه‌گانهٔ موجود report.ts از دادهٔ قطعی، با فیلتر سرور-سمت برای حریم خانواده.
3. **بدون تب تازه و بدون تراشیدن نقشهٔ mutation**: موتور خروجی صفحهٔ خودگردان از page-head + آرشیو داخل خودِ خط زمانی؛ خطوط ۳۶۶-۳۷۳ دست‌نخورده می‌مانند و فقط یک mutation تازه اضافه می‌شود.
4. **گزارش در تاریخچه «سند» است نه رویداد**: kind `report_export` با ref به snapshot و بازکردن نسخهٔ قطعی از خود تاریخچه؛ فیلتر گزارش خروجی به ۹ فیلتر موجود اضافه می‌شود.
5. **سیم‌کشی به‌جای بازتعریف**: هیچ گزارشی از صفر ساخته نمی‌شود؛ G1/G2 از موتورهای موجود صدا زده می‌شوند و بخش‌های یتیم پرونده (مدارک، تمرین، پرسشنامه، کمیسیون) با قرارداد ReportSection به آن‌ها وصل می‌شوند — چیزی که تا امروز در هیچ جمع‌بندی خروجی نبود.
