# runbook drill بازیابی ماهانه (ف۴ — انتشار ۱.۲۵.۷۰)

> ثبت رسمیِ بند «برنامهٔ بازیابی بکاپ (restore drill)» طرح ارتقای بک‌اند — §۶-آیتم ۶
> («بازیابی‌پذیری: drill ماهانهٔ restore — تنها معیار واقعی سلامت بکاپ») و §۴ آیتم P1-7.
> اسکریپت: `scripts/restore-drill.mjs` · npm: `npm run restore:drill`.
> اصل ثبت‌شده: **بکاپِ تست‌نشده = بکاپِ نیست** — این drill فقط اعتبارسنجیِ فایل است و
> هیچ پایگاه داده‌ای (محلی یا پروداکشن) را نمی‌نویسد؛ پس هر هفته هم بی‌خطر است، ولی
> **حداقل ریتم رسمی: ماهی یک‌بار** و پس از هر انتشار شامل مایگریشن جدید.

## ۱) چه چیزی بررسی می‌شود

| بررسی | جزئیات |
|---|---|
| قالب و نسخهٔ پاکت | `format = gh-backup` و `format_version = 1` — هم‌قرارداد سرویس پشتیبان سامانه |
| شمارش ردیف‌ها | `row_count` اعلام‌شدهٔ هر جدول باید دقیقاً با طول آرایهٔ `rows` برابر باشد |
| checksum پایدار | SHA-256 روی JSON قطعی (کلیدهای مرتب، بازگشتی) برای هر جدول + کل پاکت — بین ماه‌ها قابل مقایسه |
| هم‌خوانی اسکیما | جدول‌های فایل ↔ `CREATE TABLE`های `migrations/*.sql` (نام‌های گذرای `X_new→RENAME` کنار گذاشته می‌شوند)؛ جدول ناشناخته = FAIL |
| RTO | ساعت‌دیواریِ کل اعتبارسنجی — ثبت در گزارش |

خروجی: گزارش فارسی در `docs/reports/restore-drill-<YYYY-MM-DD>.md` با **مُهر بازیابی‌پذیری** (PASS/FAIL).
کد خروج اسکریپت فقط با PASS صفر است — قابل استفاده در CI یا اسکریپت ماهانه.

## ۲) گرفتن فایل پشتیبان (منشأ drill)

**مسیر الف — از خودِ سامانه (پیش‌فرض):**
1. با حساب مدیر وارد شوید و `GET /api/backup/export?include_files=0` را بگیرید
   (پنل پشتیبان `#/backup` دکمهٔ دانلود دارد؛ فایل `backup-YYYYMMDD-HHmm.json` است).
2. همان فایل را دست‌نخورده به drill بدهید. برای drillهای داخلی، نسخهٔ بدون فایل‌های پیوستی کافی است
   (جدول سنگین `exercise_file_chunks` مستثنا می‌شود و در گزارش ثبت می‌شود)؛ یک‌بار در سال با `include_files=1` هم drill بگیرید.

**مسیر ب — از Cloudflare (خارج از سامانه، برای استقلال):**
```bash
npx wrangler d1 export center-system-db --remote --output backups/prod-YYYY-MM-DD.sql
```
خروجی SQL است، نه پاکت gh-backup — برای drill، مسیر الف مرجع است؛ مسیر ب برای بایگانی خام دور از سامانه.
(اگر روزی drill مستقیمِ فایل SQL لازم شد، ابزارش به همین اسکریپت اضافه می‌شود — نه جایگزینیِ قالب.)

**مسیر ج — محلی (تمرین/بدون دسترسی پروداکشن):**
```bash
npm run migrate:local && npm run seed:local   # D1 محلی wrangler را می‌سازد/به‌روز می‌کند
npm run backup:local                          # سرویس واقعی export روی D1 محلی → backups/local-backup-*.json
npm run restore:drill -- --file backups/local-backup-*.json --note "D1 محلی + seed"
```
`backup:local` از ترنسپایلِ esbuildِ همان سرویس export سامانه استفاده می‌کند — فایلش واقعی است نه ساختگی.

## ۳) اجرای drill و خواندن مُهر

```bash
npm run restore:drill -- --file <backup.json> --report docs/reports/restore-drill-<YYYY-MM-DD>.md --note "خروجی زندهٔ پروداکشن، <تاریخ>، توسط <نام>"
```
- `--report` اختیاری است (پیش‌فرض همان مسیر بالا با تاریخ UTC امروز)؛ `--note` منشأ فایل را در گزارش ثبت می‌کند — همیشه بنویسید.
- **PASS ✅:** همهٔ بررسی‌ها سبز؛ گزارش را کامیت کنید (همین evidence در مخزن، شاهد ماه است).
- **قاعدهٔ مقایسهٔ checksum:** checksum جدولی که در آن ماه تغییر داده‌ای نداشته باید ثابت بماند؛
  ثابت‌ماندنِ غیرمنتظره یا تغییرِ غیرمنتظره هر دو پرسش می‌خواهند.

## ۴) FAIL یعنی چه — قدم‌های نخست

FAIL یعنی فایل پشتیبانِ آن ماه **به‌عنوان مسیر بازیابی قابل اعتماد نیست** — بلافاصله این‌ها را انجام دهید:

| علامت | معنا | قدم نخست |
|---|---|---|
| «قالب فایل/نسخهٔ قالب» FAIL | فایل از سامانهٔ دیگری یا نسخهٔ دیگر است | فایل را دوباره از مسیر الف بگیرید؛ اگر همان شد، سرویس پشتیبان را بازبینی کنید |
| «شمارش جدول X» FAIL | `row_count` با ردیف‌ها نمی‌خواند — خروجی ناقص/قطع‌شده | دانلود را تکرار کنید؛ بررسی حد میانی شبکه/سقف حجم؛ اگر تکرار شد، لاگ `backup.export.failed` را ببینید |
| «هم‌خوانی اسکیما» FAIL (جدول ناشناخته) | فایل از اسکیمایی که مایگریشنش در مخزن نیست | نسخهٔ مخزنِ هنگام گرفتن پشتیبان را پیدا کنید؛ فایل مشکوک به دست‌کاری است |
| «هم‌خوانی اسکیما» WARN (جدول‌های کهنه غایب) | پشتیبان از نسخهٔ قدیمی‌تر سامانه | نرمال است — در گزارش ثبت می‌ماند؛ فقط اگر سند پشتیبانِ ماه «به‌روز» بود، مطرح است |
| JSON پارس نمی‌شود | فایل بریده/خراب در انتقال | دوباره بگیرید؛ انتقال را با checksum اطراف تعویض کنید |

بعد از هر FAIL: فایل سالم تازه بگیرید و drill را تکرار کنید تا PASS — سپس گزارشِ FAIL و علتش را هم
کنار گزارش PASS نگه دارید (شاهد پیش‌آمده). اگر پس از تلاش معتبر هیچ فایل سالمی به‌دست نمی‌آید،
این یک **حادثهٔ بازیابی‌پذیری** است — همان روز اطلاع دهید؛ راه فوری: پشتیبانِ خودکارِ شبانهٔ بله
(`backup_destinations`) را از مقصدها دریافت و با همین drill بیازمایید.
