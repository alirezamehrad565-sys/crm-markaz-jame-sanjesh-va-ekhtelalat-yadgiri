# طراحی چهارگانهٔ دسکتاپ: نشانگر سرور محلی + اتصال ابری Cloudflare + ارتقای درون‌برنامه‌ای + پل CI «main → rust»

> منشأ: گزارش تست کارفرما روی v1.27.06 (۱۴۰۴/۰۸/۲۳) — «برنامه بالا می‌آید و عملکرد بدی ندارد؛ اما
> نشانگری از وضعیت سرور محلی نیست، جایی برای تنظیم Cloudflare نیست، و دو طراحی تازه می‌خواهیم:
> ارتقای نرم‌افزاری بدون آسیب به دیتا، و پل خودکار تغییرات فرانت‌اند main به اپلیکیشن rust.»
> این سند فقط **طراحی** است — پیاده‌سازی پس از تأیید نقاط تصمیم §۵ آغاز می‌شود.

## ۰. وضعیت موجود (زمینهٔ کد — طراحی روی این‌ها سوار می‌شود، نه از صفر)

| دارایی موجود | محل | نقش در این طراحی |
| --- | --- | --- |
| درگاه بوت boot-dist (RTL فارسی «در حال راه‌اندازی») | `desktop/src-tauri/boot-dist/` = `frontendDist` | تنها UI که همیشه هست — حتی وقتی موتور نیامده؛ لایهٔ اول نشانگر |
| نگهبان Rust با FSM ده‌وضعیتی + رویدادهای تائوری (`engine:restarting`، `engine:degraded`، …) | `desktop/src-tauri/src/engine.rs`، `lib.rs` | منبع حقیقت وضعیت؛ فقط یک فرمان خواندن وضعیت و یک رویداد دوره‌ای کم دارد |
| پنل سلامت فرانت + بنر نگهبان (`installEngineWatchdogBanner`، `engineSignalView`، `healthToneView`) | `public/assets/js/views/health-panel.js` + `src/__tests__/front-sync-status.test.ts` | لایهٔ دوم نشانگر؛ گسترش داده می‌شود |
| قرارداد هم‌گامی node-sync با CP (`GET /api/node-sync/status` — synced/catching_up/offline/error/idle) | `src/application/cp-sync/`، `api-routing/` | الگوی قرارداد اتصال ابری؛ ورکر CF همتای همین قرارداد می‌شود |
| باندل‌های ورکر ابری آمادهٔ استقرار (central + games، بدون دیپلوی — تصمیم با کارفرما) | `worker/central-bundle.js`، `worker/games-bundle.js`، `wrangler.games.toml` | در حالت «توکن کامل» همان‌ها با CF API دیپلوی می‌شوند |
| مایگریشن‌های D1 شماره‌دار (`0001_initial.sql` …) | `migrations/` | در ساخت خودکار D1 از همین‌ها اعمال می‌شود |
| snapshot پشتیبان JSON با quick_check (`db-snapshot.mjs` + بازیابی تأییدشده) | `scripts/engine/db-snapshot.mjs` | قالب هم‌گامی میز→ابر؛ بدون خلق قالب دوم |
| ریلیز گیت‌هاب + آرتیفکت نصاب NSIS + usb-pack | Actions، Releases | کانال توزیع ارتقا و خروجی پل CI |
| گیت‌های desktop-check ①…⑪ + شبیه‌ساز نصاب + cargo test | `scripts/desktop-check.mjs` | هر قابلیت تازه = پین/گیت تازه در همین چرخه |

**نکتهٔ کلیدی معماری:** فرانت اپ از خود موتور سرو می‌شود؛ یعنی اگر موتور نیاید فرانت هم نمی‌آید.
پس «نشانگر روشن/خاموش بودن سرور» نمی‌تواند فقط داخل فرانت باشد — باید دو لایه داشته باشد:
لایهٔ بوت (boot-dist، همیشه در دسترس) و لایهٔ فرانت (پس از بوت موفق).

## ۱. طرح A — نشانگر وضعیت سرور محلی + کنترل راه‌اندازی

### ۱-۱. قرارداد تازهٔ پوسته ↔ فرانت (سمت Rust)
- فرمان `engine_status` (invocation، بدون وضعیت جهانی تازه — از همان نگهبان می‌خواند):
  `{ "state": "Booting|Validating|Starting|Ready|Degraded|Recovering|Failed|…", "port": 8787,
     "gamesPort": 8788, "startedAtUnix": 173…, "lastEventAtUnix": 173…,
     "degradedReason": "games_unhealthy|null", "appVersion": "1.27.6" }`
- رویداد `engine:status` — با هر تغییر وضعیت FSM و همچنین یک‌بار در ثانیهٔ ۳۰ (دوپینگ نگه‌دارنده
  برای وب‌ویوای که ممکن است رویدادی را گم کند).
- فرمان `engine_restart` — همان مسیر نگهبان موجود (بدون مسیر تازهٔ کد اجرا).
- **توقف دستی در فاز اول طراحی نمی‌شود** — «خاموش کردن سرور» یعنی بستن برنامه؛ دکمهٔ توقف
  کاذب حالت‌های نیمه‌خاموش می‌سازد که فرانت را هم می‌کُشد. فقط راه‌اندازی دوباره.

### ۱-۲. لایهٔ بوت — boot-dist (همیشه‌موجود)
- یک pill وضعیت ثابت گوشهٔ صفحه: سبز «سرور محلی روشن است — آدرس localhost:8787» /
  زرد «در حال راه‌اندازی…» / قرمز «سرور بالا نیامد» + پیام شکست بوت موجود (نام‌وبنام، درس ۱.۲۷.۰۴).
- دکمه‌ها: «راه‌اندازی دوباره» (`engine_restart`)، «بازکردن پوشهٔ دیتا» (فرمان تازهٔ
  `open_data_dir` — با `explorer.exe` ویندوز)، «کپی اطلاعات عیب‌یابی» (نسخهٔ اپ، وضعیت FSM،
  خط آخر engine.log، نسخهٔ node — در کلیپ‌بورد؛ برای پیوست در گزارش).
- پس از بوت موفق، صفحهٔ اصلی موتور جایگزین می‌شود (رفتار فعلی) — pill بوت فقط در حالت
  غیر-Ready دیده می‌شود.

### ۱-۳. لایهٔ فرانت — پنل سلامت موجود گسترش می‌یابد
- نشانگر همیشه‌نمایان در سربرگ اپ (نه فقط بنر خطای گذرا): همان نگاشت `healthToneView`
  موجود — سبز Ready، زرد Degraded با دلیل، قرمز Failed/Recovering. کلیک → بازشدن پنل سلامت.
- کارت تازهٔ «سرور محلی» در پنل سلامت: وضعیت + پورت‌ها + نسخهٔ اپ/موتور + زمان آخرین بوت +
  دکمهٔ «راه‌اندازی دوباره» + «کپی اطلاعات عیب‌یابی» + «بازکردن پوشهٔ دیتا».
- در حالت وب (بدون پوستهٔ میز — سرور خودمیزبان) این کارت «حالت وب» خاکستری می‌شود:
  `engine_status` و رویدادها غایب‌اند؛ `engineSignalView` گزینهٔ `desktop_absent` می‌گیرد.

### ۱-۴. گیت‌ها
- تست نگاشت حالت→برچسب/رنگ عین الگوی `front-sync-status.test.ts` (تابع خالص، بدون DOM).
- پین desktop-check ⑪: رشته‌های `engine_status`، `engine:status`، `open_data_dir` در سورس.
- شبیه‌ساز: بوت موفق باید وضعیت Ready را در لاگ شبیه‌سازی هم ثبت کند (خروجی گیت ⑩).

## ۲. طرح B — اتصال ابری Cloudflare: دو حالت + هم‌گامی دوسویه + کلون (تصمیم‌های کارفرما اعمال شد)

### ۲-۱. جایگاه معماری (تصمیم قطعی)
- **ورکر ابری = خودِ سامانه در نسخهٔ کلادفلر، بدون پوستهٔ rust** — همان اپ (Hono + D1)؛
  باندل موجود `worker/central-bundle.js` همین است. ابر یک «نمونهٔ کامل سامانه» است،
  نه یک endpoint میرور و نه مقصدی تازهٔ همان قرارداد CP.
- **CP سایت جداست و جدا می‌ماند**: CP اطلاعات همهٔ نودها/نصب‌ها را برای جمع‌آوری سازمانی
  می‌گیرد. هم‌گامی میز↔ابر از قرارداد CP جدا است و قرارداد خودش را دارد (`instance-sync`).
- هر دو حالت ورودی (A1 و B1) با هم ساخته می‌شوند؛ انتخاب در **صفحهٔ پیکربندی اولیه**.
- ذخیره‌گاه هر دو سو هم‌شِماست (`migrations/`) — پس هم‌گامی = هم‌گامی دو نمونهٔ هم-schema.

### ۲-۲. حالت B1 — «مرکز قبلاً ورکر دارد → کلون به نسخهٔ آفلاین»
- سناریو: مرکزی که سامانهٔ ابری فعال دارد، نسخهٔ دسکتاپ آفلاین را نصب می‌کند.
- ورودی در پیکربندی اولیه (صفحهٔ boot-dist پس از نصب، وقتی dataDir فاقد تنظیم ابری است):
  آدرس پایهٔ ورکر + توکن مدیریت (= runtime-secret همان ورکر).
- وارسی: `/health` + هم‌خوانی نسخهٔ schema (فهرست مایگریشن‌های اعمال‌شده سمت ابر) + echo احراز.
- **کلون ابر→میز**: خروجی snapshot (قالب `db-snapshot.mjs` با quick_check سمت ابر) →
  اعمال مایگریشن‌های محلی تا هم-schema → import snapshot در dataDir (عین منطق بازیابی
  تأییدشدهٔ موجود) → بوت → از این‌جا دو سو با هم‌گامی دوسویه هم‌گام می‌مانند.
- قانون سخت: کلون هرگز روی دیتای محلیِ غیر-خالی بی‌پرس‌وپاسخ انجام نمی‌شود — اگر dataDir
  دیتا دارد: پیام + تأیید صریح کاربر + بکاپ محلی پیش از هر جایگزینی.

### ۲-۳. حالت A1 — «مرکز جدید → ساخت خودکار ورکر با نام دلخواه، در پیکربندی اولیه»
- سناریو: مرکز جدید از صفر — همان صفحهٔ پیکربندی اولیه، گزینهٔ «ساخت ورکر جدید».
- ورودی کاربر: **نام دلخواه ورکر** (sanitise به پیشوند `markaz-<نام>`) + API Token کلادفلر
  با اسکوپ حداقلی: `Workers Scripts:Edit` + `D1:Edit` + `Account Settings:Read`.
- زنجیرهٔ خودکار (هر گام با پیام فارسی و توقف امن در شکست):
  ۱. وارسی توکن (`/user/tokens/verify`) + فهرست اکانت‌ها؛ بیش از یکی → کاربر انتخاب می‌کند.
  ۲. ساخت دیتابیس D1 با نام انتخابی + ثبت `database_id`.
  ۳. اعمال مایگریشن‌ها از `migrations/*.sql` به‌ترتیب شماره (D1 HTTP API `/query` batch).
  ۴. آپلود `worker/central-bundle.js` با bindingهای D1 + `RUNTIME_SECRET` تصادفی
     تولیدشده سمت میز (به کاربر یک‌بار نشان داده می‌شود).
  ۵. آپلود `worker/games-bundle.js` + فعال‌سازی `workers.dev` + وارسی `/health` هر دو.
  ۶. ثبت نتیجه در `dataDir/install-manifest.json` (فیلد `cloud`) → ادامه به هم‌گامی دوسویه.
- قواعد سخت: فقط دارایی‌های با پیشوند `markaz-` ساخته یا حذف می‌شوند؛ اسکوپ توکن پیش از
  هر گام دوباره وارسی می‌شود؛ لاگ redacted (توکن هرگز)؛ secret پس از نمایش یک‌بار فقط در
  **Windows Credential Manager** (crate `keyring`) — هرگز در فایل JSON ساده.
- نام ورکر **فقط انگلیسی** (`[a-z0-9-]`، پیشوند پیش‌فرض `markaz-`) — بدون تبدیل اسلاگ فارسی
  (تصمیم کارفرما ۱۴۰۴/۰۸/۲۴: کد پیچیده نشود؛ نام غیرمعتبر در فرم رد می‌شود).

### ۲-۴. هم‌گامی دوسویه میز↔ابر (تصمیم قطعی: دوسویه؛ «دیتای زودترتشکیل‌شده برندهٔ تداخل»)
- **قاعدهٔ قطعی تداخل (تصمیم ۱۴۰۴/۰۸/۲۴ — سبک pull/push گیت‌هاب با داور زمانی):** در تعارض
  تغییرِ همان ردیف، نسخهٔ **زودترتشکیل‌شده** برنده است: مقایسهٔ `COALESCE(created_at,
  updated_at)` — کوچک‌تر برنده؛ تساوی → updated_at کوچک‌تر برنده؛ تساوی → hash کانونی JSON
  بزرگ‌تر (داور قطعی و متقارن — هر دو سو به نتیجهٔ یکسان می‌رسند؛ بدون ستون device روی
  ردیف‌ها). حذف با tombstone: deleted_at در برابر updated_at ردیف با همان داور. هیچ ردیفی
  بی‌سروصدا نمی‌افتد: نسخهٔ بازنده با **payload کامل** در `_sync_conflicts.loser_payload`
  آرشیو و شمارش تعارض‌ها در پنل سلامت نمایش داده می‌شود.
- نشست هم‌گامی مثل pull/push گیت‌هاب: state → pull چانکی → اعمال با داور → همگرایی echo
  (پاسخ push، وضعیت نهایی برندهٔ هر pk را برمی‌گرداند تا بازندهٔ push به برنده برسد) →
  push چانکی؛ cursorها فقط پس از تراکنش موفق جلو می‌روند — شکست = ادامهٔ امن از سرِ مکان.
- الزامات schema: ستون `updated_at` در جداول دامنه (مایگریشن تازه برای جداول فاقد) +
  جدول tombstone `_sync_deleted(table, pk, deleted_at, device_id)` برای حذف‌ها +
  `device_id` per install (UUID در dataDir، ثبت در install-manifest.json).
- انحراف مستند (فاز B — مأموریت SB2): مایگریشن 0114 **بدون trigger** است — سیاست مخزن
  «مایگریشن‌ها بدون trigger و بدون تراکنش دستی» (گیت check-d1-compat ①/⑬) بر طرح trigger سه‌گانهٔ
  هر جدول مقدم شد؛ ابر بدون trigger کار می‌کند (سرویس‌ها `updated_at = datetime('now')` و حذف نرم
  `deleted_at + updated_at` را خودشان می‌نویسند — الگوی finance/service.ts؛ helper
  `recordSyncTombstone` فقط برای DELETEهای سخت) و نسخهٔ فقط-میز همان triggerها در
  `scripts/engine/local-triggers.sql` است که بوت موتور محلی پس از مایگریشن‌ها best-effort اعمال
  می‌کند — این فایل هرگز وارد migrations/ یا schema.sql نمی‌شود.
- پروتکل `instance-sync` (هر دو سو همان باندل مرکزی را سرو می‌کنند — قرارداد دوسویه):
  `GET /api/instance-sync/state` (cursorها + نسخهٔ schema) ·
  `POST /api/instance-sync/pull` (ردیف‌های updated_at>cursor + tombstoneها، per-table) ·
  `POST /api/instance-sync/push` (batchهای `INSERT OR REPLACE` + tombstone، chunked با سقف
  اندازهٔ درخواست) — احراز = runtime-secret + شناسهٔ device؛ پاسخ هر فراخوانی = وضعیت
  per-table. فهرست جداول هم‌گامی در یک کانفیگ صریح (جدول + PK + ستون updated_at).
- اجرا: موتور محلی (adapter) هم‌گامی را می‌راند (همان‌جا که SQLite مستقیم دارد) — دستی با
  دکمهٔ «هم‌گام‌سازی اکنون» + خودکار دوره‌ای پس از بوت (پیش‌فرض ۱۰ دقیقه، پیکربندی‌شدنی).
- پیش از هر اعمال: snapshot بکاپ سمت میز؛ پس از اعمال: شمارش per-table + `quick_check`
  سمت ابر → وضعیت synced/error در کارت. cursorها در جدول `_sync_state` روی **هر دو سو**
  نگه داشته می‌شوند (انحراف آگاهانه از طرح اولیهٔ `dataDir/sync-state.json`: تراکنشی با
  اعمال است و رفتار دو سو یکسان؛ هر شکست → cursorها دست نمی‌خورند — هم‌گامی از سرِ امن).
- سینک **زمان‌دار** (تصمیم کارفرما ۱۴۰۴/۰۸/۲۴): خودکار دوره‌ای هر ۱۰ دقیقه (پیکربندی‌شدنی،
  کف ۱ دقیقه) + دکمهٔ دستی «هم‌گام‌سازی اکنون».

### ۲-۵. UI — جریان پیکربندی اولیه (پیاده‌سازی فاز C — v1.27.۰۹)
- **مسیر تازهٔ SPA: `#/cloud-setup`** (ویزارد «پیکربندی اتصال ابری» — فقط-مدیر، lazy):
  گام ۱ انتخاب با سه کارت: «اتصال به ورکر ابری موجود» (B1)، «ساخت ورکر تازه با توکن
  کلادفلر» (A1)، «فقط محلی» (skip — بدون قفل، قانون سند v1.26.0). گام B1: فرم آدرس + رمز
  یک‌بارمصرف + فاصلهٔ سینک → ذخیرهٔ config → secret به Credential Manager (فرمان
  `cloud_secret_set`) → «هم‌گام‌سازی اکنون» → کارت وضعیت. گام A1: توکن API (مجوزها:
  Workers Scripts:Edit + D1:Edit + Account Settings:Read) + نام دلخواه با اعتبارسنجی زندهٔ
  فقط-انگلیسی و پیش‌نمایش پیشوند `markaz-` → وارسی توکن و انتخاب حساب → گام نمایش رمزها
  (**AUTH_SECRET و NODE_SETUP_TOKEN فقط یک‌بار** — کپی + هشدار نگه‌داری امن) → «ذخیره و
  اتصال» → کارت وضعیت. گام پایانی: وضعیت زنده + پیوند پنل سلامت.
- **نقاط ورود سه‌گانه**: بنر داشبورد (فقط مدیر، فقط وقتی ابر تنظیم نشده، رد کردن سشن‌محلی)،
  هدایت خودکار یک‌بار در نخستین اجرا (فلگ `cloudSetupSeen`)، دکمهٔ «پیکربندی اولیه…» در کارت
  ابری پنل سلامت؛ پانویس boot-dist هم در حالت «موتور آماده» پیوند می‌دهد.
- **بک‌اند A1 (پرویژن)**: adapter با binding `CLOUD_PROVISION` دو فایل ثابت نصب
  (`central-worker.js` + `schema.sql` از `resources/engine/central/`) را به اپ می‌دهد؛
  مسیرهای فقط-مدیر `POST /api/instance-sync/provision/verify` و `POST /api/instance-sync/provision`
  هر هفت گام CF API را می‌رانند (وارسی توکن → حساب → D1 موجود/ساخت → اسکیما قطعه‌قطعه
  ≤۶۴KB در مرز «;» → آپلود ورکر با bindings `DB`(D1) + `AUTH_SECRET` + `NODE_SETUP_TOKEN`
  → فعال‌سازی workers.dev → سلامت `/healthz` + `instance-sync/state` با Bearer). در حالت
  وب/ابربinding غایب → **۵۰۱** با پیام «فقط دسکتاپ». توکن/رمزها در steps و لاگ هرگز نمی‌آیند
  («***»)؛ وابستگی صفر — CF client تزریقی fetch (تست با API فیک، بدون تماس واقعی در CI).
- کارت «اتصال ابری» در پنل سلامت کنار کارت سرور محلی (دو کارت جدا — دو قرارداد جدا):
  حالت اتصال، آخرین هم‌گامی دوطرفه، تعداد تعارض‌های `_sync_conflicts` با فهرست، دکمهٔ
  «هم‌گام‌سازی اکنون»، «پیکربندی اولیه…»، «حذف اتصال» (تأیید دوبله + پشتیبان).
- تنظیمات کلیدها: پس از ذخیره در Credential Manager فقط «●●●●آخرین ۴ رقم» نمایش داده می‌شود.

### ۲-۶. گیت‌ها
- تست قرارداد نگاشت/چانک‌ساز/قاعدهٔ FWW (تابع خالص در vitest — winner resolution باید
  متقارن و قطعی باشد: هر دو سو روی ورودی یکسان به یک برنده می‌رسند) + یک شبیه‌ساز CF فیک
  (سرور محلی در تست که رفتار D1 API و endpoints ورکر را مقلد می‌کند — بدون تماس واقعی در CI).
- پین desktop-check: رشته‌های `instance-sync`، `_sync_conflicts`، `device_id`، `keyring`،
  پیشوند `markaz-`.
- audit: ردیف `cloud.sync` / `cloud.deploy` / `cloud.clone` با نتیجه و تعداد ردیف — بدون
  هیچ توکن. مایگریشن‌های تازه (updated_at / tombstone / conflicts) طبق قاعدهٔ مایگریشن‌ها.

## ۳. طرح C — ارتقای درون‌برنامه‌ای OTA (بدون آسیب به دیتا)

### ۳-۱. دو کانال (هر دو از همان ریلیز گیت‌هاب تغذیه می‌شوند)
1. **کانال خودکار**: پلاگین رسمی `tauri-plugin-updater` — endpoint فایل `latest.json` در
   ریلیز گیت‌هاب، دانلود نصاب NSIS، وارسی امضای minisign، اجرا، راه‌اندازی دوباره.
   کلید خصوصی آفلاین (نگه‌داری با کارفرما)، کلید عمومی داخل اپ؛ امضا در CI از secret.
2. **کانال دستی** (همیشه موجود — برای ماشین با لایهٔ AV): دکمهٔ «بررسی نسخهٔ تازه» →
   مقایسهٔ نسخه با ریلیز Latest → نمایش تغییرات (بدنهٔ ریلیز) → دکمهٔ «دانلود نصاب از
   مرورگر» (بازکردن صفحهٔ ریلیز) → اجرای دستی. هیچ دانلودی از داخل اپ به‌عنوان تک‌مسیر
   نیست — درس ریسک ۴ (AV ایران).
3. **UX کانال‌ها (تصمیم کارفرما ۱۴۰۴/۰۸/۲۴)**: کانال stable = اطلاع‌رسانی + نصب **دستی** با
   یک کلیک؛ کانال hot (آینده — فقط تغییرات فرانت) = نیمه‌خودکار (دانلود خودکار + نصب با یک
   کلیک). انتخاب کانال در تنظیمات → Updates.

### ۳-۲. قواعد سختِ «بدون آسیب به دیتا»
- نصاب per-user NSIS فعلی فقط شاخهٔ برنامه را لمس می‌کند؛ **dataDir بیرون از شاخهٔ نصب
  است و هیچ گام ارتقا آن را نمی‌بیند** — این را یک پین تازه در desktop-check می‌بندد
  (پین: هیچ مسیری از کد ارتقا به dataDir ندارد).
- پیش از هر ارتقا: snapshot بکاپ quick_check (همان ابزار موجود) + ثبت در audit.
- پس از ارتقا و بوت موفق: مُهر سلامت در `install-manifest.json` (فیلد `lastHealthyVersion`).
- شکست بوت پس از ارتقا: پیام + «نصب ریلیز قبلی از گیت‌هاب» — ریلیزهای N-1 و N-2 نگه
  داشته می‌شوند (همان روال حذف ریلیز قبلی، با بافر دو نسخه).
- بررسی به‌روزرسانی **هرگز در مسیر بوت نیست** — فقط با دکمهٔ دستی یا پس از بوت موفق در
  پس‌زمینه؛ آفلاین = بی‌خطا، فقط «بررسی نشد — آفلاین».

### ۳-۳. چرخهٔ انتشار
نسخهٔ تازه = بامپ هشت‌نقطه‌ای + build CI + امضا + `latest.json` + ریلیز **draft** با نصاب
→ تست کارفرما → publish دستی (عین روال امروز؛ پل §۴ همین را خودکار می‌کند).

## ۴. طرح D — پل CI «main → rust» (تغییرات فرانت‌اند به اپلیکیشن برسد)

### ۴-۱. جریان
```
push روی main (تغییر src/ / public/ / migrations/)
  └─ CI اصلی main سبز (tsc + vitest + build)
       └─ workflow_run → job «sync-pr»:
            ۱. checkout شاخهٔ rust + merge main
            ۲. تعارض؟ → PR با برچسب «تعارض» + پیام فارسی + توقف امن (هیچ pushی غیر از این)
            ۳. بامپ پچ خودکار (۱.۲۷.۰۶ → ۱.۲۷.۰۷ — همان هشت‌نقطه‌ای)
            ۴. گیت‌ها روی نتیجهٔ merge: tsc + vitest + desktop-check (شامل شبیه‌ساز)
            ۵. build ویندوز + امضا + latest.json
            ۶. ریلیز draft + یادداشت خودکار (فهرست کامیت‌های main + «دسکتاپ vX»)
            ۷. PR sync با نتیجهٔ گیت‌ها — تأیید شما → merge → ریلیز draft آمادهٔ تست
```
- **یافتهٔ ۱۴۰۴/۰۸/۲۳ — تاریخ‌های rust و main جدا (unrelated histories) هستند**: merge درختی
  یعنی اتحاد دو درخت و گیت بودجهٔ عملکردی روی این ترکیب می‌شکند (نمونهٔ واقعی: در ریلیز
  ۱.۲۷.۰۷، اجرای pull_request قرمز شد در «بودجهٔ کارایی» در حالی که اجرای push و بیلد ویندوز
  همان کامیت سبز بودند — قرمزیِ merge-اتحاد، نه قرمزی ریلیز).
  پس پل CI **merge درختی ندارد**: انتقال تغییر فرانت main به rust با اعمال پچ path-scoped
  (فقط `src/` و `public/` از دیف کامیت‌های main با `git diff`/apply یا cherry-pick محدود) +
  بامپ + گیت‌ها + ریلیز draft؛ و PR تعارض‌دار ساختاری حذف می‌شود (workflow فقط روی rust
  و مسیرهای فرانت اجرا می‌شود).
- قاعدهٔ سخت: پل هرگز merge درختی rust↔main نمی‌کند و هرگز مستقیم به rust push نمی‌کند —
  خروجی پچ روی PR بررسی و با merge خود PR ثبت می‌شود (نقطهٔ بازبینی باقی می‌ماند).
- تداخل محتوایی داخل merge تصمیم پل نیست — قاعدهٔ §۵-۴ (زودترتشکیل‌شده) فقط برای دیتای
  هم‌گامی است؛ کد همان push مستقیم main است (main منبع حقیقت فرانت‌اند).
- تعارض محتمل نیست (rust فقط desktop/ و scripts/desktop را به main اضافه می‌کند و src/ را
  کم تغییر می‌دهد)؛ اگر شد، PR تعارض‌دار دستی حل می‌شود — خودکار حل‌نشده رها نمی‌شود.

### ۴-۲. گیت‌های تازه
- پین: workflow تازهٔ `sync-main-to-rust.yml` شامل «desktop-check» و «draft release».
- قانون: ریلیز draft فقط از CI ساخته می‌شود؛ publish همیشه دستی کارفرما (رنگ آزمایشی
  از تأیید کارفرما جدا می‌ماند).
