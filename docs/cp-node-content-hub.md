> **وضعیت (به‌روز ۱۴۰۵/۰۸/۱۸):** سمت نود 1.25.46 کامل و سبز است؛ سمت CP هم با انتشار

## ۱) چیستی

محور دوم «فاز غنی‌سازی»: CP بهترین محتوای آموزشی/درمانی را از مراکز **جمع** می‌کند،
**کیوریشن** می‌کند و **به مراکز دیگر توزیع** می‌کند. سه نوع محتوا:

| kind | معنا | منبع محلی مرجع |
|---|---|---|
| `exercise` | تمرین / کارت آماده | بانک تمرین (منوی «کارت‌های آماده») |
| `plan` | طرح درمان (پروتکل جلسه‌به‌جلسه) | `pathway_templates` / طرح درمان |
| `doc` | سند خام اداری/آموزشی | منوی «نمون‌برگ‌ها و اسناد خام» |

فایل پیوست (PDF/تصویر) در نسخهٔ ۱ از مرز عبور نمی‌کند — فقط متن ساختارمند
(`title/summary/body/tags`). انتقال فایل به نسخهٔ بعدی قرارداد موکول است.

## ۲) متغیرها و خاموشی

هیچ متغیر env تازه‌ای معرفی نمی‌شود؛ همان کلید نود m1.2:

- `CP_SYNC_URL` (فقط origin آن مصرف می‌شود) · `CP_NODE_CODE` · `CP_NODE_KEY`
- `CP_SYNC_STAFF_ID` — سازندهٔ نمایشی ردیف‌های cp در نود (اختیاری؛ پیش‌فرض `cp-content`)

هر سه متغیر اول خالی باشد → ماژول صفر کار می‌کند (kill switch بدون دیپلوی).

## ۳) مسیر انتقال

Service Binding `CP` (ورکر به ورکر، هم‌حساب) اگر موجود باشد؛ وگرنه fetch عمومی.
همان الگوی سینک اعلان‌ها — خطای 1042 کلادفلر برای fetch هم‌زون با binding حل شده است.

## ۴) درگاه ① — همرسانی نود → CP (push)

```
POST {origin}/api/node/content/submit
X-CP-Node-Code: <node code>
Authorization: Bearer <node key>
X-CP-Node-Version: 1.25.46
Content-Type: application/json
```

```json
{
  "items": [
    {
      "id": "UUID محلی نود",
      "kind": "exercise | plan | doc",
      "title": "≤ ۱۵۰ نویسه",
      "summary": "≤ ۶۰۰ نویسه",
      "body": "≤ ۸۰۰۰ نویسه — متن ساختارمند",
      "tags": ["≤ ۸ برچسب، هر کدام ≤ ۴۰ نویسه"],
      "submitted_at": "ISO UTC",
      "source_ref": "null یا ارجاع به آیتم محلی (مثلاً exercises.id)"
    }
  ]
}
```

- حداکثر ۲۰ آیتم در هر دسته (`CP_CONTENT_BATCH_MAX`)؛ ترتیب قدیمی‌ترین صف → جدیدترین.
- پاسخ `2xx` یعنی CP پذیرفته (صف کیوریشن) → نود ردیف‌ها را `status='submitted'` می‌کند.
- پاسخ غیر 2xx یا خطای شبکه → ردیف‌ها در `queued` می‌مانند و دورهٔ بعد دوباره تلاش می‌شود.
- CP باید بر اساس `node code` + `id` دوباره‌ارسالی را idempotent بنشیند (UPSERT توصیهٔ CP سمت خودش).
- ردیف‌های `withdrawn`‌شدهٔ محلی هرگز push نمی‌شوند؛ کنارگذاری پس از push فعلاً از
  مسیر تیکت/مدیریت CP است (نسخهٔ ۲: پیام `retract`).

## ۵) درگاه ② — برگزیده‌ها CP → نود (pull)

```
GET {origin}/api/node/content/sync?since=<ISO UTC>
# since = آخرین سینک موفق − ۶۰ ثانیه؛ دورهٔ اول بدون since
# همان هدرهای نود (X-CP-Node-Code / Authorization / X-CP-Node-Version)
```

پاسخ:

```json
{
  "data": {
    "server_time": "ISO UTC — مُهر سینک موفق نود",
    "items": [
      {
        "id": "cp-content-… (پیشوند اجباری)",
        "kind": "exercise | plan | doc",
        "title": "…", "summary": "…", "body": "…",
        "tags": ["…"],
        "active": true,
        "source_center": "کد مرکز مبدأ یا null (ناشناس)",
        "created_at": "ISO UTC",
        "updated_at": "ISO UTC"
      }
    ]
  }
}
```

- حداکثر ۱۰۰ آیتم در پاسخ (قرارداد؛ CP با `CONTENT_LIST_MAX_LIMIT=100` صفحه می‌دهد —
  آیتم‌های `updated_at > since` برگردانده شوند).
  **یادداشت ۱۴۰۵/۰۸/۲۰ (بازبینی طرح ارتقا — CP-1):** کد نود از ۱.۲۵.۴۸ سقف پاسخ pull را با
  ثابت دستهٔ push (`CP_CONTENT_BATCH_MAX=20`) بسته — ناسازگار با همین بند و با رفتار CP
  (`cp-repo/src/domain/content/service.ts:924`)؛ شواهد کامل در
  `docs/backend-upgrade-plan-2026-11-11.md` §۳-۶. رفع شد در انتشار **۱.۲۵.۶۷** با ثابت جدا
  `CP_CONTENT_PULL_MAX=100` (+ سه آزمون سقف)؛ درگاه push همان ≤۲۰ می‌ماند.
- **قانون طلایی (دو لایه دفاع):** فقط `id` با پیشوند `cp-content-` نوشته می‌شود —
  لایهٔ اول فیلتر JS بعد از Zod، لایهٔ دوم گارد SQL در UPSERT:
  `WHERE network_content.id LIKE 'cp-content-%'`.
- `active:false` یعنی بایگانی (ستون `active=0`) — حذف فیزیکی ممنوع.
- ترتیب اعمال: قدیمی→جدید (`updated_at` صعودی) تا جدیدترین برنده باشد.
- UPSERT کامل است: ویرایش عنوان/محتوا در CP در دورهٔ بعد روی همهٔ نودها می‌نشیند.

## ۶) ریتم و مُهرها

- یک دورهٔ کامل (push + pull) حداکثر هر **۱۵ دقیقه**: کرون مشترک `CP_SYNC_CRON` و
  دروازهٔ فرصت‌طلب روی ترافیک زنده — مُهر مشترک `settings`:
  - `cp_content.last_attempt_at` — رگولاتور ۱۵دقیقه‌ای
  - `cp_content.last_push_at` / `cp_content.last_sync_at` — آخرین موفقیت هر جهت
- ترتیب داخل دوره: اول push (صف مرکز زودتر می‌رود) بعد pull؛ خطای هر جهت خطای دیگری نیست.
- هر خطا = `log.warn` فقط؛ نود هرگز به‌خاطر CP کرش یا کند نمی‌شود.

## ۷) جدول نود و نمایش

- جدول `network_content` (مایگریشن 0098) — هم ردیف‌های محلی (`origin='local'`,
  وضعیت‌های `draft→queued→submitted/withdrawn`) و هم برگزیده‌ها (`origin='cp'`,
  `status='published'`) را نگه می‌دارد.
- نمای «کتابخانهٔ شبکه» در پنل (فقط مدیر): تب همرسانی + تب برگزیده‌های شبکه؛
  آیتم‌های بایگانی‌شده از فهرست پنهان‌اند ولی در جدول می‌مانند.
- ممیزی: ساخت/صف/کنارگذاری محلی در `audit_log` با `action LIKE 'network_content.%'`.

## ۸) گیت‌های آزمون نود (سبز)

`src/application/cp-content/__tests__/cp-content.test.ts` + `e2e-network-content.test.ts`:
خاموشی کامل · گیت ۱۵دقیقه‌ای · فیلتر پیشوند دو لایه · UPSERT و بایگانی ·
push فقط-صف · خطای مستقل push/pull · ۴۰۴ CP = استقلال کامل · گیت نقش‌ها (مدیر/منشی) ·
عدم‌تغییرشدنیِ ردیف cp از مسیرهای محلی.

## ۹) چک‌لیست سمت CP (فاز بعدی)

1. دو درگاه فوق با همان احراز m1.2 (`X-CP-Node-Code` + Bearer) — بدون کلید تازه.
2. جدول صف کیوریشن + وضعیت (received → reviewed → curated/rejected).
3. پاسخ idempotent به `submit` (کلید `(node_code, id)`).
4. توزیع = انتشار ردیف با `id` پیشونددار `cp-content-` و `active:true`؛ حذف = `active:false`.
5. صفحه‌بندی pull با `since` و سقف ۱۰۰.
6. بازگشت رأی/وضعیت کیوریشن به نود (نسخهٔ ۲ قرارداد).
