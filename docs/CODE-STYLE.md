# قانون کامنت‌نویسی (CODE-STYLE)

این سند قرارداد کامنت‌نویسی کل مخزن است — بک‌اند (`src/`)، فرانت (`public/assets/js/`)، سرور خودمیزبان (`server/`) و اسکریپت‌ها (`scripts/`).

## ۱) زبان

- کامنت‌ها **فارسی محاوره‌ای ساده** هستند — همان‌طور که پای میز کار به همکار می‌گویید: «اگه»، «برمی‌گردونه»، «می‌شه». نه فارسی کتابی، نه انگلیسی.
- شناسه‌ها، تایپ‌ها، امضای توابع و پیام‌های خطا انگلیسی می‌مانند؛ فقط کامنت فارسی است.
- اصطلاح فنی جاافتاده انگلیسی اشکالی ندارد: ISO UTC، soft delete، race condition، idempotent و امثال آن.

## ۲) کامنت «چرا» می‌گوید، نه «چه»

کد خودش «چه» را نشان می‌دهد؛ کامنت فقط وقتی ارزش دارد که دلیل یا تله را توضیح دهد:

```ts
// ❌ بد — تکرار کد
n = Math.min(n, 50); // n را سقف می‌زند

// ✅ خوب — دلیل را می‌گوید
n = Math.min(n, 50); // سقف page_size — ورودی abc قبلاً LIMIT NaN و خطای ۵۰۰ می‌ساخت
```

## ۳) ارجاع به تصمیم‌ها

اگر کامنت به یک تصمیم محصول یا قرارداد design.md وصله است، مقصد را با نام بگویید، نه با شماره؛ و همیشه «دلیل» را بنویسید، نه فقط اشاره:

```ts
// ✅ گارد NaN (?page_size=abc قبلاً LIMIT NaN و ۵۰۰ می‌ساخت)
```

## ۴) ممنوع‌ها

- کامنتی که فقط کد را به زبان دیگری تکرار می‌کند.
- شروع «This function ...» یا هر شکل دیگری از کامنتِ خودکار و انبوه.
- بنر ASCII و جداکننده‌های تزئینی طولانی.
- ایموجی در کامنت — تنها استثنا: ⚠️ برای تلهٔ واقعی و نادر.
- بلاک کد کامنت‌شده به‌عنوان «شاید بعداً لازم شد» — تاریخ گیت حافظهٔ ماست.

## ۵) سرپرست فایل

فایل‌های بزرگ یا الگوریتمی (موتورها، pure های چندصدخطی، هارنس تست) یک کامنت ۲–۳ خطی بالای فایل می‌گیرند: این فایل مسئول چیست و به کدام ماژول وصل است. فایل‌های کوچکِ خودگویا سرپرست لازم ندارند — کامنتِ بی‌دلیل خودش بوی بد است.

## ۶) تازگی

کامنت نباید کهنه شود: اگر منطق عوض شد، کامنتِ همان خط در **همان کامیت** آپدیت یا حذف می‌شود. کامنتِ غلط از بی‌کامنتی بدتر است.
