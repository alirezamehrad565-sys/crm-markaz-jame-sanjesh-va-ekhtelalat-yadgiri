# POLISH-4 — مرتب‌سازی و تکمیل پروژه بدون ریسک رگسیون

> **قانون صفر (سرِ همه‌چیز):** پیش از هر نوبت کاری، سندباکس از آخرین کامیت شاخه‌ی rust بازسازی می‌شود (`git fetch + reset --hard origin/rust`). هیچ‌وقت روی اسنپ‌شات قدیمی‌تر از آخرین کامیت کار نمی‌کنیم؛ هر نوبت با کامیت و push تمام می‌شود.
>
> **قانون رگسیون:** هیچ تغییر ساختاری بدون دروازهٔ سبز اجرا نمی‌شود: typecheck + سوییت کامل vitest + build سه‌گانه (client/worker/engine-server) + desktop-check. حذف کد فقط با آزمون قفل‌شدهٔ رفتار قبلی.

## وضعیت مبدأ (۱۹ نوامبر ۲۰۲۶ — پس از POLISH-3)

| شاخه | نسخه | وضعیت |
|---|---|---|
| `rust` | ۱.۲۷.۳۰ | کانن توسعه — POLISH-3 کامل (M1–M7)، ۲۹۴۰ آزمون سبز |
| `main` | ۱.۲۵.۸۱ | ۹ کامیت انحصاری (۱.۲۵.۷۷–۸۱) که در rust نیستند |
| نقطهٔ واگرایی | `f231c16` | main ≠ زیرمجموعهٔ rust — ادغام ساده ff نیست |

**۹ کامیت انحصاری main** (باید در ادغام بیایند): کارت گرد درگ‌پذیر سنجش در تقویم، فلوی «روز قبل» سنجش روزانه، سد نوبتِ «درمانگرِ درگیر»، پاک‌سازی no-slop، FIELDS_MAX 45→120 + «پیش‌نمایش از نگاه خانواده»، CI کلادفلر (`cf-deploy.yml` با secretها و دروازهٔ سلامت).

**۱۰۷ کامیت انحصاری rust**: همهٔ خط ۱.۲۶ و ۱.۲۷ (POLISH-1/2/3، نرم‌سازی، پنل‌ها، روایت‌سازی).

قرارداد کارفرما: این دو فقط ابزار نسخهٔ میزند؛ روی وب/کلادفلر از UI قطع‌اند و کد زنده می‌ماند.

- دکمهٔ سربرگ (server-pill): از قبل فقط-میز (`window.__TAURI__`) — دست‌نخورده.
- مسیرهای `#/health-panel` و `#/cloud-setup`: با `desktopOnly()` پیچیده شدند — روی وب یادداشت نرم، روی میز عین همان پنل.
- بنر ابری داشبورد + هدایت اولین‌اجرای ابری: گارد `isDesktopShell()` قبل از fetch.
- گیت تازه: `front-platform-cut.test.ts` (۴ پین). پیوست: `docs/legacy/DISCONNECTED-PANELS.md` §۳.

نتیجه: ادغام آیندهٔ شاخه‌ها UI وب را نمی‌شکند — ویژگی‌های میزبودن از قبل در لبهٔ وب قطع‌اند.

## M3 — تک‌شاخه‌شدن و یکسان‌سازی نسخه‌گذاری ✓ (۱.۲۷.۳۲ — با تأیید کارفرما، بی‌خیال مرحله‌بندی CI، با دروازهٔ محلی کامل)

هدف کارفرما: **یک شاخه** که نرم‌افزار + دکمهٔ پنل سلامت (فقط میز) دارد، و وب/کلادفلر همان کد را با UIِ قطع‌شدهٔ پنل‌ها دیپلوی می‌کند. نسخه‌گذاری دو شاخه هم یکسان شود.

سابقهٔ تصمیم (اجراشده در ۱.۲۷.۳۲ — متن اصلی حفظ شد) **چرا merge فوری را توصیه کرده بودیم:** دو خط موازی با ۱۱۶ کامیت اختلافی و تعارض قطعی در فایل‌های بامپ‌خور (version.ts، sw.js، index.html، package*.json، tauri.conf.json، Cargo.toml، front-12561) و احتمال تعارض معنایی در فرم‌ساز (FIELDS_MAX) و no-slop (حذف‌های ۱.۲۵.۸۰ ممکن است چیزهایی را حذف کرده باشد که rust بازنویسی کرده). ادغام بدون دروازه = دقیقاً ریسک رگسیونی که کارفرما منع کرده.

**اجراهای واقعی ۱.۲۷.۳۲:** مرج origin/main→rust انجام شد (۹ فایل ویژگی/تست دوطرفه؛ ۳۸ تعارض همه «همان ویژگی در دو مسیر» و سمت rust مرج شد)؛ دو مایگریشن تکراری main (0109/0110) و دو تست کهنه (12579/12578) حذف شد؛ بقیهٔ گام‌های زیر برای انتشارهای بعدی برقرار است:

**گام‌های دروازه‌دار (هر گام با سوییت کامل سبز):**
1. شاخهٔ ادغام `unify` از سر rust + `git merge origin/main` — تعارض‌های نسخه: همیشه مقدار rust (۱.۲۷.۳۱+)؛ تعارض منطق: بازبینی فایل‌به‌فایل با آزمون‌های طرفین.
2. آشتی no-slop×rust: گزارش «حذف‌شده‌های ۱.۲۵.۸۰» در برابر نمادهای rust — هر بازگشت حذف، رد می‌شود مگر آزمون داشته باشد.
3. دروازهٔ کامل: typecheck + vitest کل (۲۹۴۰+ آزمون‌های دو طرف) + build سه‌گانه + bundle-smoke + perf-budget + csp-hash + migrations-doc + desktop-check.
4. دیپلوی آزمایشی روی workers.dev (نه تولیدی) + دودِ دستی مسیرهای کلیدی (`#/dashboard`, `#/case-event-types`, `#/cloud-setup` روی وب = یادداشت نرم).
5. `merge --ff-only` به main + اجرای دستی `cf-deploy.yml` + دروازهٔ سلامت ×۳ خودِ ورک‌فلو.
6. بعد از **دو انتشار بی‌حادثه**: rust = کانن توسعه؛ main فقط نشانگر انتشار (هر انتشار `git merge --ff-only rust`؛ هرگز کامیت مستقیم روی main).
7. نسخه‌گذاری یکسان: پس از گام ۱ فقط version.tsِ rust مرجع است؛ بامپ شش‌نقطه‌ای یک‌جا؛ main نسخهٔ مستقل ندارد (عددش = عدد rust در لحظهٔ انتشار).

**معیار لغو/توقف:** هر قرمزی دروازه که با دو تلاش سبز نشد → توقف، گزارش، تصمیم کارفرما.
