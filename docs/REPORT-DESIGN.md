# طراحی گزارش‌ساز خودکار پرونده — از ماژول‌های پراکنده تا «پرونده‌ای که خودش حرف می‌زند»

> منشأ: خواست کارفرما (۱۴۰۵/۰۹) — «برو سراغ طراحی گزارش‌های اتوماتیک برای خروجی گرفتن از پرونده؛ با استفاده از همهٔ ماژول‌ها و همهٔ کارت‌ها؛ قسمت‌های مختلف پرونده در کنار هم معنی‌دار بشوند: از تمرین تا طرح درمان تا گزارش جلسه‌به‌جلسه، پرسشنامه‌ها و آزمون‌های عملکردی.»
> روش طراحی: نگاه متخصص + ممیزی ماژول‌به‌ماژول مخزن (۳۱ ماژول دامنه، ۳۴ نما) در نسخهٔ ۱.۲۷.۴۹. مکمل سندهای [PRODUCT-STORY-CRITIQUE](./PRODUCT-STORY-CRITIQUE.fa.md) و [INTAKE-DESIGN](./INTAKE-DESIGN.md) است.
> اصل شمارهٔ یک: **گزارش، خلاصهٔ تصمیم‌دار است نه dump داده.** الگوی هر بخش: «یافته → تفسیر → تصمیم». الگوی اجرایی از `clinical-engine/report.ts` (تسلط؟ روند؟ تصمیم پیشنهادی؟ + دوز و وفاداری) گرفته شده و به کل گزارش‌ساز تعمیم می‌یابد.

---

## ۱. وضع موجود — سه موتور ناتمامِ پراکنده

امروز سه تولیدکنندهٔ خروجی در محصول هست، هرکدام جزیره‌ای:

| موجود | کجا | چه می‌دهد | چه کم دارد |
|---|---|---|---|
| گزارش دوره‌ای طرح درمان (`clinical-engine/report.ts`) | بک‌اند، خالص و read-only | تسلط/روند/تصمیم + دوز و وفاداری + پاراگراف خانواده + سه روایت از یک داده (والد/متخصص) | persist ندارد، جلسه‌به‌جلسهٔ مفصل ندارد، چاپ A4 ندارد |
| گزارش پیشرفت توانبخشی (`views/progress-report.js`) | نما، مبتنی بر چک‌لیست مهارتی | روند تسلط جلسه‌به‌جلسه (OLS)، منحنی محو راهنما، RCI، چاپ/PDF با قالب A4 | فقط مسیر درمانی را می‌بیند؛ پرسشنامه/وکسلر/تمرین/عملکردی ندارد |
| خروجی‌های چاپ جزیره‌ای (finance/center-kpi/clearbook/health-panel) | تک‌نما | چاپ جدول همان نما | بدون سرصفحهٔ پرونده، بدون پیوند روایی، بدون نسخه و امضا |

نتیجه: دادهٔ پرونده در ۳۱ ماژول هست اما «قسمت‌های مختلف پرونده در کنار هم» هرگز یک صفحه نمی‌شوند. این سند موتور چهارم را طراحی می‌کند که **روی سه‌تای بالا سوار می‌شود، جایگزینشان نمی‌شود**.

## ۲. کاتالوگ گزارش‌ها — هفت خروجی با مخاطب و دورهٔ مشخص

هر گزارش = مخاطب + دورهٔ زمانی + بخش‌های انتخابی + قالب خروجی. هیچ گزارشی «همه‌چیز برای همه» نیست؛ همین تفکیکِ مخاطب است که جلوی dump را می‌گیرد.

| کد | گزارش | مخاطب | دوره | خروجی |
|---|---|---|---|---|
| G1 | **پروندهٔ کامل** (شناسنامه تا امروز) | متخصص/پروندهٔ رسمی | کل عمر پرونده | A4 چاپ/PDF + snapshot ذخیره |
| G2 | **گزارش دورهٔ درمان** (تعمییم report.ts) | متخصص + کمیته | یک طرح درمان | A4 + پیوست نیم‌رخ |
| G3 | **گزارش جلسه** (جلسه‌به‌جلسه) | متخصص/سوپرویزن | یک جلسه یا بازهٔ N جلسه | A4 فشرده + روند |
| G4 | **گزارش تمرین و وظایف** | خانواده (زبان ساده) | یک ماه | A4 یک‌ورقه + توکن |
| G5 | **گزارش سنجش‌ها** (پرسشنامه + عملکردی) | متخصص/اداره | دوره یا مقطع | A4 + جدول مقایسهٔ دو اجرا |
| G6 | **برگهٔ پیشرفت خانواده** | خانواده | دوره | توکن‌محور فقط‌خواندنی (وب) |
| G7 | **گزارش پوشش و اداره** | مدیر/ادارهٔ آموزش | ماه/فصل | A4 + پیوست مالی ماسک‌شده |

قاعدهٔ گیت‌شدنی: **هیچ بخشی بدون «منبع دادهٔ زنده» به کاتالوگ اضافه نمی‌شود** — هر بخش باید به ماژول/کارت مبدأ وصل باشد (بخش ۳)؛ وگرنه بخش بی‌داستان است و با همان قاعدهٔ «یا حفر دارد یا می‌رود» حذف می‌شود.

## ۳. نقشهٔ داده — هر بخش گزارش از کدام ماژول/کارت می‌آید

ممیزی کامل؛ این جدول قرارداد ساخت «ReportSection» است و در پیاده‌سازی مستقیماً به فهرست fetcherها تبدیل می‌شود.

| بخش گزارش | ماژول مبدأ | نما/کارت مبدأ | خروجی بخش |
|---|---|---|---|
| شناسنامه و تاریخچهٔ تحصیلی | `student-profile` | پروفایل — تب شناسنامه | جدول هویتی + خط زمانی مدارس |
| غربال ورودی و ملاک‌های ورود | `screening` | کارت غربال | نتیجهٔ غربال + تاریخ ارجاع |
| نیم‌رخ هوش (وکسلر WISC-IV) | `wechsler-engine` | کارت وکسلر | نیم‌رخ استاندارد + تفسیر نقاط قوت/ضعف |
| باتری‌های بالینی و تشخیص (SNAP-IV/SCARED/ODD) | `clinical-engine` | کارت باتری + روایت بالینی | نمره‌ها + برچسب‌های استنتاج + فرمولاسیون |
| فرمولاسیون مورد و فرضیه‌ها | `case-formulation` | تب روایت بالینی | هم‌گرایی شواهد + فرضیه‌های رتبه‌بندی‌شده |
| چک‌لیست‌های کاردرمانی (OT) | `ot-engine` | کارت OT | وضعیت چک‌لیست + روند |
| طرح درمان و مسیر مداخله | `clinical-engine` (`targets`/`report.ts`) | نمای طرح درمان | تسلط/روند/تصمیم + دوز و وفاداری |
| جلسات و حضور | `appointment-core` + `attendance` | تقویم + بورد روز | جدول جلسات (تاریخ/مدت/وضعیت) + نرخ غیبت |
| یادداشت جلسهٔ درمانگر | `working-day` + حاشیهٔ نوبت | بورد روز | روایت جلسه‌به‌جلسه (G3) |
| تمرین‌ها و وظایف خانه | `exercise-bank` + `todos` | کارت تمرین | فهرست تمرین داده‌شده/انجام‌شده + پیوست کاربرگ |
| پارادایم‌های عملکردی (کورسی، N-back، استروپ، فلانکر، گونوگو، سیمون، اسپن، اسکن، ناملاین) | `games` | کارت هر پارادایم | جدول پارامترها + روند میان دوره |
| پرسشنامه‌ها و فرم‌های خانواده/معلم | `case-events` (`form-builder` + `survey-insights`) | کارت رویدادها | نمرهٔ مقیاس + روند CSQ-8 و هم‌خانواده‌ها |
| بلوک‌های سنجش و کمیته | `assessment-blocks` + گزارش کمیته (`reports.js`) | کارت بلوک | مصوبات کمیته + تاریخ‌های بازسنجی |
| پیگیری‌ها | `followups` | کارت پیگیری | موارد باز/سررسیده + وضعیت |
| مدارک درخواستی | `document-requests` | کارت مدارک | وضعیت sent→received→closed |
| برچسب‌ها و هشدارها | `tags` | کارت برچسب | برچسب‌های فعال پرونده |
| مالی (فقط مدیر، ماسک در G7) | `finance` | کارت مالی | کمک/فاکتور/تراز دوره |
| بستهٔ اداری و نمون‌برگ‌ها | `docs` | مخزن اسناد | پیوست اسناد الصاقی |
| کلر بوک و خط زمانی مرکز | `clearbook` | نمای کلر بوک | خط زمانی رویدادهای پرونده |
| سلامت داده و بکاپ (پیوست فنی G1) | `health-panel`/backups | پنل سلامت | مهر «آخرین بکاپ» پای گزارش |

سه ماژولِ زیرساختی (`conflict-engine`، `working-hours`، `staff`)، `announcements`/`knowledge`/`network-content`/`bug-reports`/`center-kpi` گزارش‌پرونده‌ای ندارند و در G7 فقط به‌صورت شاخص مرکز ظاهر می‌شوند — عمداً، تا پرونده بالینی بماند نه عملیاتی.

## ۴. موتور ترکیب — قرارداد ReportSection و چرخهٔ تولید

```
کاربر: انتخاب دانش‌آموز + نوع گزارش (G1..G7) + دوره + تیک بخش‌ها
  → بک‌اند: fetcher هر بخشِ تیک‌خورده → آرایهٔ ReportSection (data + verdict + hints)
  → composer: قالب مخاطب‌محور + قواعد روایت + مرتب‌سازی استاندارد (شناسنامه→سنجش→تشخیص→طرح→جلسات→تمرین→پرسشنامه→پیوست)
  → snapshot JSON (نسخه‌دار + hash) → persist در جدول report_exports + audit
  → رندر: A4 چاپی (پسوند موتور چاپ progress-report با همان tokens) + لینک توکن برای G6 + ارسال بله برای G4/G6
```

قرارداد هر بخش (هم‌سوی قراردادهای موجود):

```ts
interface ReportSection {
  key: string;                 // مثل 'wechsler_profile'
  title: string;               // عنوان چاپی فارسی
  source: string;              // ماژول مبدأ — برای گیت «منبع زنده»
  required: boolean;           // اگر داده ندارد: 'ندارم' صادقانه بنویسد یا حذف شود
  fetch(studentId, range): Promise<SectionData>;
  verdict(data): { finding: string; decision?: string }; // یافته→تصمیم — اجباری
  renderA4(data, verdict): string;  // HTML با tokens موجود چاپ
}
```

سه قاعدهٔ سخت موتور:
1. **snapshot-first**: گزارش ذخیره می‌شود (چه چیز، کی، با چه داده‌ای) — پای گزارش «نسخهٔ ۱.۲۷.۴۹ · hash · نام صادرکننده · تاریخ جلالی» می‌خورد؛ گفت‌وگوی بعدی دربارهٔ «همان گزارش» ممکن است. الگو: persist ممنوعِ report.ts را با نسخهٔ snapshot می‌شکنیم ولی دادهٔ خام همچنان از جداول زنده می‌آید.
2. **بدون جدولِ بدون حکم**: هر جدول یا یک جملهٔ verdict بالای سرش دارد یا از گزارش حذف است (همان جراحی کارت‌های داشبورد، این بار روی کاغذ).
3. **حریم با کانال گره می‌خورد**: G4/G6 به خانواده = بدون نام تشخیص DSM، بدون مالی، بدون دادهٔ پروندهٔ دیگران؛ G7 به اداره = مالی ماسک‌شده؛ G1/G2 فقط نقش‌های بالینی. RBAC از همان گارد نقش‌های `core/auth/middleware` — نقش تازه‌ای ساخته نمی‌شود.

## ۵. برنامهٔ سه‌موج اجرا

| موج | محتوا | افق |
|---|---|---|
| ۱ — ستون فقرات | قرارداد ReportSection + composer + snapshot/persist + قالب A4 مشترک + G2 (تعمیم report.ts موجود) و G3 | ~۱ هفته |
| ۲ — پوشش ماژول‌ها | بخش‌های وکسلر/عملکردی/پرسشنامه/تمرین (G5، G4) + مقایسهٔ دو اجرا در G5 | ~۱ هفته |
| ۳ — توزیع و اداره | G6 توکن‌محور + ارسال بله + G7 با پیوست مالی ماسک‌شده + آرشیو گزارش‌های صادرشده در پروفایل | ~۱ هفته |

گیت تازه‌ی پیشنهادی: آزمون e2e «هر گزارش با دادهٔ کمینه صفر بخشِ `required` حذف‌نشده و هر بخش verdict دارد» + گیت بودجهٔ چاپ (هر گزارش ≤ N صفحه).

## ۶. متخصص چه چیز دیگری می‌خواهد — فهرست قابل‌تصمیم‌گیری برای جلسهٔ کارفرما

از منظر کسی که هر روز پرونده می‌بیند و گزارش می‌دهد، این‌ها محتمل‌ترین درخواست‌های بعدی است (ترتیب = اولویت پیشنهادی):

1. **تیک‌بخش‌ها و پیش‌نمایش**: «فقط این چهار بخش را بده» + پیش‌نمایش قبل از چاپ؛ گزارشِ هر جلسهٔ کمیته متفاوت است.
2. **ویرایش متن‌ها پیش از صدور**: پاراگراف‌های verdict به‌عنوان متن قابل‌ویرایش (نه قفل‌شده) — گزارش رسمی باید صدای خود متخصص باشد.
3. **مقایسهٔ دو دوره**: «وکسلر ۱۴۰۳ در برابر ۱۴۰۵»، «نمرهٔ SNAP اجرای اول/دوم» — سطر delta با رنگ روند.
4. **امضا و مهر**: بلوک «صادرکننده/پوزیشن/تاریخ/امضا» پای هر گزارش رسمی + شمارهٔ گزارش برای پیگیری اداری.
5. **قالب ادارهٔ آموزش‌وپرورش**: قالب G7 باید با فرم گزارشِ اداره هم‌سطر شود (اگر فرم رسمی موجود است، پیوست شود).
6. **زبان دوگانهٔ خانواده**: نسخهٔ «متخصص» و نسخهٔ «والد» از همان داده — report.ts همین را با parentVariantOf آغاز کرده؛ تعمیمش به همهٔ گزارش‌ها.
7. **آرشیو در پرونده + جست‌وجو**: هر گزارش صادرشده روی خط زمانی پرونده نشیند و قابل بازیابی باشد (نه فقط فایل محلی مرورگر).
8. **ارسال امن**: دکمهٔ «ارسال با بله/لینک توکنِ منقضی‌شدنی» برای G4/G6 — نه فایل پیوست خام.
9. **پیوست نمودار خام برای سوپرویزن**: آپاندیس اختیاری با نمودارهای جلسه‌به‌جلسهٔ progress-report.
10. **خروجی اکسل خام** (پژوهش/آمار مرکز): یک G0 اداری جدا — «خروجی داده» نه «گزارش»، با سقف نقش مدیر.

## ۷. ریسک‌ها و تصمیم‌های باز

- **زیرساخت فایل**: snapshotها در `d1-store` (سقف ۵۱۲KB) جا می‌شوند؛ اگر PDF ذخیره‌شدنی شود مسیر `r2-store` از قبل هست — تصمیم باز: آیا گزارش‌ها ذخیرهٔ R2 می‌خواهند؟ (پیشنهاد: نه، snapshot JSON کافی است.)
- **قالب چاپ در مرورگرهای خانواده**: چاپ A4 موجود با `document.write` و tokens ثابت است؛ G6 توکن‌محور باید بدون لاگین رندر شود — همان الگوی `public-form.ts`، نه صفحهٔ جدید.
- **دادهٔ قدیمی خراب**: report.ts برای رکورد بدون `done_at` قاعدهٔ مستند دارد؛ composer همان قاعدهٔ «مهر ملاک گزارش» را برای همهٔ بخش‌ها یکسان می‌کند.
- **انتظار «اتوماتیکِ کامل»**: بخش‌هایی مثل روایت جلسه دست‌مکتوب‌اند؛ اتوماتیک یعنی «جمع‌بندی و فرمت خودکار + متن بالینی از انسان» — این مرز باید در جلسه با کارفرما پذیرفته شود، وگرنه گزارش بی‌روح می‌شود.
