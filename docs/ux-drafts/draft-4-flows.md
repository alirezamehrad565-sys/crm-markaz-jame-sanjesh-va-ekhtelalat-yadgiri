# طرح ۴ — «فلوهای هدایت‌شده» (ردیف ریشهٔ گیج‌کنندگی: فرم‌ها و مودال‌های چندگانه)

> مأموریت: کارفرما گفته «خیلی امکانات توی پروندهٔ دانش‌آموز گیج‌کننده است؛ فلوها، جای دکمه‌ها و تعامل طراحی بهتر لازم دارد؛ شاید کل بخش باید طراحی مجدد شود.»
> پاسخ این طرح: پرونده را بازطراحی کامل نمی‌کنیم؛ **هر عمل پرتکرار را به یک فلوی گام‌به‌گام چندمرحله‌ای با «مرور پیش از ثبت» تبدیل می‌کنیم** و صفحهٔ اصلی فقط به سه پرسش بزرگ جواب می‌دهد. مودال‌های موجود حذف نمی‌شوند — به گامِ فلو تبدیل می‌شوند.
> پایه‌ها: [PROFILE-FLOW-MAP.md](../PROFILE-FLOW-MAP.md) · [PROFILE-UPGRADE-DESIGN.md](../PROFILE-UPGRADE-DESIGN.md) · [PROFILE-GLOSSARY.md](../PROFILE-GLOSSARY.md)
> شواهد کد این سند از: `public/assets/js/views/student-profile.js` (۱۹۱۵ خط)، `public/assets/js/case-events.js`، `public/assets/js/exercise-send.js`، `public/assets/js/student-teachers.js`.

## قواعد الزامی این طرح (چک‌ناپذیر نیستند)

1. **RTL کامل؛ موبایل‌محور:** هر چینش اول برای ۳۷۵px طراحی شده و دسکتاپ گسترش آن است.
2. **صفر رشد بوت:** فلوی‌ها در chunk داینامیک (الگوی `games-console.js` / `student-narrative.js`)؛ هیچ import eager تازه‌ای به بوت اضافه نمی‌شود؛ `eager_modules` همان ۷ می‌ماند.
3. **بدون endpoint تازهٔ سنگین:** همهٔ فلوها فقط endpointهای موجود را می‌کوبند (فهرست شواهد در §۵). یک endpoint خواندنیِ سبک برای «پیش‌نمایش گزارش» در موج C اختیاری است و بدون آن هم طرح برقرار می‌ماند.
4. **واژگان فقط از واژه‌نامه:** متن‌های تازه فقط با واژگان [PROFILE-GLOSSARY.md](../PROFILE-GLOSSARY.md)؛ واژه‌های تازهٔ این طرح در §۹ فهرست شده‌اند و طبق قاعدهٔ «د» واژه‌نامه، **اول به واژه‌نامه می‌روند، بعد به کد** (گیت `scripts/ui-voice-check.mjs`).
5. **RBAC موجود بدون نقش تازه:** مدیر / منشی / درمانگر / معلم / خانواده؛ ماتریس دسترسی فلوها در §۱۰.
6. **دیپ‌لینک‌ها حفظ:** `#/students/:id?tab=…` با کلیدهای `info | clinical | narrative | timeline | sessions | exercises | games | comms` + `?filter=followups` + نام مستعار `?tab=followups` — همه بدون تغییر.
7. **قرارداد بازسازی بی‌صدا ۱.۲۰.۰:** فلوی‌ها فقط با callbackهای موجود `onSaved/onSent/onChanged` بنشینند؛ نقشهٔ دستی `rerenderTabIf([...])` دست نمی‌خورد.
8. **حریم خانواده:** در واریانت خانوادهٔ گزارش و متن پیام‌ها، تشخیص DSM/مالی ممنوع (همان گارد سند REPORT-DESIGN).

## §۱ ① معماری اطلاعات — سه پرسش، یک ایستگاه

صفحهٔ اصلی پرونده فقط سه پرسش را جواب می‌دهد؛ هر چیز دیگری یا در تب‌ها (خانهٔ ثابت) است یا پشت منوی فلو:

```
پروندهٔ دانش‌آموز
├── کارت هویت (نام، بج‌ها، مسئول پرونده، مسیر)              ← «چه گذشت؟» سطح صفر
├── ★ ایستگاه اقدام (جایگزین انباشت دکمه‌ها در کارت وضعیت)
│   ├── پرسش ۱: «الان چه باید بکنم؟» — سه ردیف معلقِ واقعی (از دادهٔ حاضر؛ بدون fetch تازه)
│   │     ۱. پیگیری عقب‌افتاده/باز (بج شمار)  → فلوی ۲
│   │     ۲. جلسه‌های گذشتهٔ بی‌گزارش (بج شمار) → فلوی ۱ (prefill نوبت)
│   │     ۳. جلسهٔ پیش رو (تاریخ + برگهٔ جلسه)  → فلوی ۱
│   ├── پرسش ۳: «چه می‌خواهی ثبت کنی؟» — دکمهٔ «شروع ثبت» → منوی فلو:
│   │     ثبت جلسه · ثبت رویداد/فرم · ارسال چک‌لیست · ارسال تمرین · پیام به معلم/خانواده · صدور گزارش قطعی
│   └── سرصفهٔ «خروجی‌ها»: آخرین «گزارش قطعی — شمارهٔ …» + شمار آرشیو «گزارش‌های خروجی»
├── پرسش ۲: «چه گذشت؟» — سرصفهٔ فصل جاری (از chapters موج ۱) + نقطهٔ کلیدی آخر + «جدیدها»
│     → دکمهٔ «تاریخچهٔ کامل» به تب تاریخچه (دیپ‌لینک حفظ)
├── تب‌ها (کلیدها و رندررها ثابت — فقط گروه‌بندی ذهنی عوض می‌شود)
│     اطلاعات پایه · تفسیر بالینی · روایت بالینی · تاریخچه · جلسات · تمرین‌ها · بازی‌ها · ارتباطات
└── کارت مدارک (خودگردان — دست نمی‌خورد)
```

اصل طراحی: **هر عمل پرتکرار یا یک فلو دارد یا یک خانهٔ ثابت؛ هیچ عملی دو رابط متفاوت ندارد.** مدخل هم‌برچسب‌هم‌رفتار در زمینهٔ تب (مثل «ثبت گزارش» روی هر ردیف نوبت) مجاز است، چون همان فلوی واحد را با prefill باز می‌کند.

## §۲ ② چینش نماها (موبایل‌محور + دسکتاپ)

### موبایل (۳۷۵px — طراحی اولیه)

```
┌──────────────────────────────────────┐
│ ← پروفایل دانش‌آموز        [خروجی‌ها] │  ← page-head سبک؛ «صدور گزارش قطعی» به ایستگاه منتقل
│ ┌──────────────────────────────────┐ │
│ │ نام و بج‌ها  (مسئول، مسیر، نیاز)  │ │  ← کارت هویت؛ دکمهٔ «ویرایش» یکتا در همین کارت
│ └──────────────────────────────────┘ │
│ ┌──── ایستگاه اقدام ★ ──────────────┐ │
│ │ الان چه باید بکنم؟                │ │
│ │ ⚑ پیگیری عقب‌افتاده (۲)  [ثبت نتیجه]│ │  ← هر ردیف: یک خط، یک دکمهٔ اصلی، بج شمار
│ │ ⚑ ۳ جلسهٔ گذشتهٔ بی‌گزارش [شروع]    │ │

│ │ [        شروع ثبت  ▾        ]      │ │  ← منوی فلو (bottom-sheet در موبایل؛ full-width)
│ │ خروجی‌ها: گزارش قطعی شمارهٔ ۱۲ · آرشیو(۴)│ │
│ └──────────────────────────────────┘ │
│ چه گذشت؟ دورهٔ درمان ۲ — حضور ۸۳٪ … [تاریخچهٔ کامل]│  ← سرصفهٔ فصل جاری + «جدیدها»
│ [تب‌ها — نوار کشیدنی افقی، swipe]     │
│ [محتوای تب فعال]                      │
│ [کارت مدارک]                          │
└──────────────────────────────────────┘
```

### دسکتاپ (≥۹۹۲px)

دو ستون RTL: **ایستگاه اقدام ستون راستِ چسبان (`position: sticky`، عرض ~۳۲۰px)** و ستون چپ محتوای تب‌ها. کارت هویت روی هر دو ستون کشیده می‌شود. در دسکتاپ ردیف‌های سه‌گانهٔ «الان چه باید بکنم؟» همه یکجا دیده می‌شوند؛ در موبایل فشرده به بج‌های شمار و بازشدن با ضربه.

### رفتار ایستگاه اقدام (دقیق)

- **داده‌ها از حافظهٔ نما:** ردیف پیگیری از `timeline.nextAction` و آیتم‌های `open` خط زمانی (همان منطق `buildSessionSheet` خط ۸۴۳ و صف پیگیری `paint()` خط ۷۲۲)؛ ردیف بی‌گزارش از `noteApptIdSet()` و `eventsOfAppt()`؛ ردیف جلسهٔ پیش رو از `appointments` — **صفر fetch تازه** (همان تعهد موج ۲ سند ارتقا).
- **حالت خالی صادقانه:** اگر هیچ معلقی نباشد، ایستگاه فقط می‌گوید «معلقی نیست — گزارش جلسات و پیگیری‌های این پرونده به‌روز است.» (واژهٔ برگهٔ جلسه، خط ۸۹۲) و بلوک خالی نسازد — همان قاعدهٔ «بدون placeholder».
- **RBAC در ایستگاه:** ردیف‌ها و آیتم‌های منوی فلو قبل از رندر با گاردهای موجود (`canCreateCaseEvents`, `canSendReport`, `canManageTags`, `canManageCase`, `canCompleteFollowup`) فیلتر می‌شوند؛ گزینهٔ معلول‌شدهٔ بی‌توضیح نداریم.
- **معلقِ پنهان نمی‌شود:** اگر ردیفی برای نقش کاربر قابل اقدام نیست (مثلاً منشی و رویداد)، فقط **بازدید** می‌ماند نه اقدام — دکمه‌ای که خطا بدهد رندر نمی‌شود.
- **فلو = wizard در همان مودال:** هر فلو یک `openModal` چندگامی است (گام‌ها با نوار پیشرفتِ بالای مودال، دکمهٔ «بازگشت» و Esc) — نه صفحهٔ جدید؛ پس دیپ‌لینک تب فعال نمی‌شکند و `rerenderTabIf` دست‌نخورده می‌ماند.

| **A — ایستگاه و یکتاسازی مدخل‌ها** | کارت وضعیت → ایستگاه اقدام (سه ردیف + منوی «شروع ثبت» + سرصفهٔ «خروجی‌ها»)؛ برگهٔ جلسه به ایستگاه می‌رود؛ حذف مدخل‌های تکراری (ثبت رویداد ×۳→۱، ویرایش/برچسب/هدف ×۲→۱، تاریخچهٔ تحصیلی ×۲→۱)؛ «حذف پرونده» به منوی «بیشتر» | فقط `student-profile.js` + رندر ایستگاه در chunk داینامیک | صفر | دیپ‌لینک‌های هر ۸ تب سبز؛ `ui-voice-check` سبز؛ perf صفر بایت؛ smuke میوتِیشن‌ها |

| **C — فلوی گزارش قطعی با مرور** | بازسازی `openSnapshotBuilder` به گام‌های انتخاب مسیر → مرور/واریانت/امضا → قطعی؛ مودال پیش‌نیاز مسیر صفر حفظ | همان فایل + فلو در `flows.js` | صفر (اختیاری: endpoint خواندنی سبک «پیش‌نمایش» همان سازندهٔ sections بدون INSERT — با اجازهٔ کارفرما) | بازتولید عین هش snapshot؛ تست حریم واریانت خانواده؛ «تاریخ قطعی/اصالت سند» دست‌نخورده |
| **D — فلوی ارتباطات واحد** | ادغام مودال «گزارش معلم» + کارت «پیام آزاد» + مدخل چک‌لیست در فلوی ۴ (گیرنده → محتوا → مرور → ارسال)؛ کارت‌های اتصال بله دست‌نخورده | `flows.js` + حذف دو رابط قدیمی پس از استقرار | صفر (teacher-report/family-report/case-events send/progress-sheet موجود) | تست هر چهار endpoint خروجی؛ پیامک بدون تلفن معلول با توضیح؛ آرشیو رویدادهای پیام در خط زمانی |

قاعدهٔ بین‌موجی: هر موج قبل از حذف رابط قدیمی، دو هفته هر دو مسیر «هم‌رفتار» هستند (برچسب یکسان)، بعد رابط کهنه فقط با مودال قدیمی حذف می‌شود — شانس بازگشت صفر خطا.

## §۶ ⑥ ریسک‌ها

| ریسک | اثر | کاهش |
|---|---|---|

| رگرسیون در قرارداد بازسازی بی‌صدا ۱.۲۰.۰ | پرش اسکرول / رندر دوبارهٔ کل نما | ویزاردها فقط با callbackهای موجود `onSaved/onSent/onChanged` نتیجه را برمی‌گردانند؛ هیچ فلو مستقیماً `selectTab` نمی‌کند |
| کهنگی دادهٔ `appointments` (سقف ۵۰، بدون cursor) | نوبت قدیمی‌تر در فلوی ۱ دیده نمی‌شود | اظهار صادقانه + دیپ‌لینک تقویم؛ پیشنهاد آینده: cursor (خارج از این طرح) |

| RBAC ناهمگن پیگیری (POST فقط مدیر/منشی) | درمانگر گزینهٔ معلول می‌بیند | گارد قبل از رندر؛ گزینهٔ «پیگیری جدید» فقط برای مدیر/منشی |
| رشد بوت با ویزاردها | نقض بودجهٔ perf | همهٔ فلوها یک chunk داینامیک؛ بارگذاری فقط با اولین بازکردن ایستگاه؛ هیچ eager تازه |

## §۷ ⑦ سه سنجهٔ کاهش گیجندگی + «کلیک تا ثبت»

1. **شاخص یکتایی مدخل (DTI):** برای هر «عمل» شمار رابط‌های متفاوتِ بازکنندهٔ آن در یک صفحه. امروز: ثبت رویداد ۳ رابط، پیام به معلم ۳ رابط، ویرایش هدف/برچسب ۲ رابط. هدف پس از موج A و D: **DTI = ۰ رابط متفاوت برای هر عمل** (مدخل هم‌برچسب‌هم‌رفتار زمینه‌دار مجاز). سنجش: شمارش استاتیک دکمه‌ها در اسکریپت سموک (تاثیر پایه: `student-profile.js` خطوط ۲۷۲/۵۸۶/۷۵۶/۱۰۹۴/۱۱۲۵/۱۱۷۶/۱۴۰۴).
2. **نرخ پایان بدون انحراف (پایلوت کاربر):** ۵ کاربر روزمره (۲ منشی، ۲ درمانگر، ۱ مدیر) × ۴ مأموریت؛ سنجه: سهم مأموریت‌هایی که بدون بازگشت/انحراف تا «ثبت موفق» پیش می‌روند ≥ ۸۰٪. پایهٔ قبل از موج B یک‌بار اندازه‌گیری و پین می‌شود.
3. **بار اقدام خط اول:** شمار دکمه‌های اقدامِ هم‌زمانِ دیده‌شده بالای خط اول پرونده. امروز: ۶ دایره + ۲ دکمه + منوی بله + select مسئول ≈ ۹ سطح تصمیم. هدف: **≤ ۴** (سه ردیف ایستگاه + منوی «شروع ثبت»)؛ باقی یا تاشو یا در تب.
4. **جدول «کلیک تا ثبت» (هدف پین‌شده در سموک):**

| فلو | امروز (مسیر واقعی کد) | هدف فلو | یادداشت |
|---|---|---|---|
| ثبت جلسه | ~۳-۴ کلیک + بدون حضور و بدون مرور (حضور از نما ممکن نبود) | **≤۵ (معمول ۳) + n ورودی** — حالا با حضور و مرور | مرور جای کلیکِ برهنهٔ اضافه را با حذف جست‌وجوی مدخل می‌خرد |
| پیگیری عقب‌افتاده | ۲ کلیک برای رسیدن به صف + ثبت نتیجهٔ تک‌جوابی بی‌زمینه | **۳ تا ۴** با سه گزینهٔ نتیجه و زمینه | |
| صدور گزارش قطعی | ۲ کلیک — بی‌بازبینی، واریانت بعد از قطعی | **۳ تا ۴** — مرور و واریانت قبل از شماره‌گرفتن | یک کلیک عمداً اضافه می‌شود: ریسک بی‌بازگشت حذف می‌شود |
| گزارش به معلم/خانواده | ~۳ کلیک در سه رابط متفاوت با سه منطق گیرنده | **۴ + متن** در یک رابط واحد | گیرنده‌محور، پیش‌نمایش متن + کانال |

قاعدهٔ بودجهٔ کلیک: هیچ فلو نباید از امروزِ خودش بیش از ۱ کلیک کندتر شود؛ اگر گام ایمنی کلیک اضافه می‌کند، باید یک کلیکِ بی‌ثمر (پیمودن تب‌ها برای یافتن مدخل) را حذف کند — هر چهار فلو بالا همین‌طور مهندسی شده‌اند.

## §۸ دیپ‌لینک‌ها و سازگاری (چک‌لیست موج A)

- کلیدهای تب و `knownTabs` (خط ۳۸۴) ثابت؛ `?tab=followups` و `?filter=followups` عیناً به تاریخچه با صف پیگیری می‌روند.
- لندینگ نقش‌محور درمانگرِ مسئول (برگهٔ جلسه؛ خطوط ۳۹۳-۴۰۱) به لندینگ ایستگاه بازآدرس می‌شود ولی شرط‌هایش همان است (فقط صاحب پرونده + نوبت ۴۸ ساعت آینده).
- `KIND_LINKS`، گارد نسل F2، seen-at «جدیدها»، «گزارش‌های خروجی» در خط زمانی — دست‌نخورده.

## §۹ واژه‌های تازهٔ این طرح — اول واژه‌نامه، بعد کد

| واژهٔ تازه | جا | تعریف روزمره |
|---|---|---|
| ایستگاه اقدام | کارت سه‌پرسشی صفحهٔ اصلی | جایی که می‌گوید «الان چه باید بکنم» و فلو را باز می‌کند |
