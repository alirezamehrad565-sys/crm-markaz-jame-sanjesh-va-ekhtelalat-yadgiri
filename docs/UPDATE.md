# راهنمای به‌روزرسانی (Update Guide) — سامانهٔ مرکز جامع

سایت و بات شما روی Cloudflare زنده است. این سند توضیح می‌دهد چطور هر نسخهٔ جدید را
**بدون هیچ ریسکی برای دیتابیس** روی همان استقرار بنشانید. این کار سه دقیقه طول می‌کشد
و هر تعداد که بخواهید قابل تکرار است.

> این سند برای «به‌روزرسانیِ استقرارِ موجود» است. نصب از صفر → [`DEPLOY.md`](./DEPLOY.md).

---

## ۱) ایدهٔ کلی — چرا دیتابیس خراب نمی‌شود؟

سه محافظ روی دادهٔ شما قرار دارد:

1. **مایگریشن نسخه‌دار و ردیابی‌شده:** تغییرات اسکیما فقط از طریق فایل‌های
 `migrations/NNNN_name.sql` می‌آیند. خودِ D1 در جدول داخلی `d1_migrations`
 ثبت می‌کند کدام مایگریشن‌ها قبلاً اعمال شده‌اند؛ پس `migrations apply` همیشه
 **فقط فایل‌های جدید** را اجرا می‌کند و روی دادهٔ موجود کاری ندارد.
2. **قانون «افزودنی» (additive):** ما در مایگریشن‌ها فقط جدول/ستون ایندکس
 **اضافه** می‌کنیم (`CREATE TABLE IF NOT EXISTS`، `ALTER TABLE ADD COLUMN`)؛
 حذف داده (DELETE/DROP روی جدول‌های واقعی) هرگز بخشی از انتشار نیست —
 حتی مایگریشن‌های پاکسازی (مثل 0026) فقط ساختار ماژول حذف‌شده را برمی‌دارند.
3. **پشتیبان پیش از هر تغییر:** چرخهٔ به‌روزرسانی قبل از هر دست‌زدنی به دیتابیس،
 یک خروجی کامل SQL از پایگاه تولید می‌گیرد و در `backups/` نگه می‌دارد.
 بدترین حالت، همیشه یک فایل بازگشت دارد.

> قواعد طلایی که رعایتشان کافی است:
> اسکیمای دستی (`--file=` یا `execute`) روی تولید **اجرا نکنید**؛
> secrets (توکن بات) و `database_id` روی حساب Cloudflare می‌مانند و با باندل جابه‌جا نمی‌شوند.

## ۲) مسیر سریع — یک فرمان (توصیه‌شده)

باندل جدید (مثلاً `center-system-.zip`) را باز کنید، داخل پوشه:

```bash
npm install # فقط بار اول در هر باندل
node scripts/update-remote.mjs
```

اسکریپت چهار گام را با پرسش «y/n» جلو می‌برد:

| گام | کار | جزئیات |
|-----|-----|--------|
| ۰ | پیش‌پرواز | ورود wrangler، درج خودکار `database_id` از حساب (اگر جای‌نگهدار باشد)، فهرست مایگریشن‌های در انتظار |
| ۱ | پشتیبان | `wrangler d1 export` → `backups/backup-<زمان>.sql` |
| ۲ | مایگریشن | فقط مایگریشن‌های جدید — روی پایگاه به‌روز، هیچ |
| ۳ | انتشار | `wrangler deploy --var ENV:production` |
| ۴ | تأیید | `GET /health` → مقایسهٔ نسخهٔ زنده با نسخهٔ باندل |

کلیدهای کمکی:

```bash
node scripts/update-remote.mjs --yes # بدون پرسش (اتوماتیک)
node scripts/update-remote.mjs --dry-run # تمرین بی‌خطر — فقط دستورها را نشان می‌دهد
node scripts/update-remote.mjs --backup-only # فقط پشتیبان‌گیری (هر وقت خواستید)
node scripts/update-remote.mjs --skip-backup # بدون پشتیبان — فقط برای deploy تکراری همان روز
```

## ۳) مسیر دستی — پنج فرمان

اگر ترجیح می‌دهید خودتان گام‌به‌گام بروید:

```bash
# ۰) (یک‌بار) database_id واقعی داخل wrangler.toml بگذارید — از «npx wrangler d1 list» بگیرید

# ۱) پشتیبان کامل دیتابیس
npx wrangler d1 export center-system-db --remote --output=backups/backup-$(date +%F).sql

# ۲) مایگریشن‌های جدید (فقط جدیدها اعمال می‌شوند — امن برای تکرار)
npx wrangler d1 migrations apply center-system-db --remote

# ۳) انتشار نسخهٔ جدید
npx wrangler deploy --var ENV:production

# ۴) تأیید: نسخهٔ زنده باید با باندل یکی باشد
curl https://<your-worker>.<your-subdomain>.workers.dev/health
```

پاسخ `/health` چنین است:

```json
{ "ok": true, "version": "0.41.0", "milestone": "", "ts": "..." }
```

- نسخهٔ زنده = نسخهٔ باندل → به‌روزرسانی کامل شد.
- پانویس سایدبار سامانه هم همین نسخه را نمایش می‌دهد.

## ۴) چه چیزهایی بین باندل‌ها «می‌ماند»؟

این‌ها را با باندل جدید بُر نزنید؛ روی حساب Cloudflare شما زنده‌اند:

| چیز | کجا زندگی می‌کند | چه‌وقت لمس می‌شود |
|-----|------------------|--------------------|
| دادهٔ واقعی (دانش‌آموز، نوبت، سنجش، …) | D1 | هرگز با کد جابه‌جا نمی‌شود |
| `database_id` | `wrangler.toml` خودتان | فقط بار اول (اسکریپت خودکار درج می‌کند) |
| `BALE_BOT_TOKEN` و `BALE_WEBHOOK_SECRET` | Secrets کلادفلر | فقط بار اول (`wrangler secret put`) |
| webhook بات بله | سرور بله | فقط بار اول (`setWebhook`) |
| `PUBLIC_BASE_URL` و `CLINIC_NAME` | `wrangler.toml` خودتان | اگر دامنه عوض شد |

پس موقع باز کردن باندل جدید: فقط اگر تغییراتی در `wrangler.toml` باندل لازم است
(متغیر جدید معرفی‌شده در یک نسخه — در یادداشت انتشار اعلام می‌شود)، آن یک خط را
به `wrangler.toml` خودتان اضافه کنید؛ بقیهٔ فایل خودتان را نگه دارید.

## ۵) بازگشت به عقب (Rollback)

- **کد:** باندل قبلی را باز کنید و فقط `npx wrangler deploy --var ENV:production`
 بزنید — انتشار فوری به نسخهٔ قبل برمی‌گردد. (مایگریشن‌ها را دستی برنگردانید؛
 مایگریشن‌های افزودنی با کدِ قدیمی هم بی‌ضررند.)
- **دیتابیس:** فایل پشتیبان `backups/backup-*.sql` هست؛ بازیابی را با هم انجام
 می‌دهیم — پیش از هر اقدام، خروجی `wrangler d1 list` و نام فایل پشتیبان را
 برای من بفرستید.

---

## ۶) چیزی که سمت من (توسعه) رخ می‌دهد

هر نسخهٔ جدید در همین گفتگو ساخته می‌شود:

1. شما تغییر/فیچر را می‌خواهید → من در مخزن همین‌جا پیاده و تست می‌کنم
 (typecheck + ۸۱۰+ تست).
2. اگر اسکیمای D1 تغییر کند → **مایگریشن جدید** `migrations/0027_….sql` با قانون
 افزودنی — هرگز فایل مایگریشن قبلی ویرایش نمی‌شود.
3. نسخه bump می‌شود (`package.json` + `src/core/version.ts` + پانویس سایدبار +
 `?v=` در `index.html`).
4. باندل `center-system-mNN.zip` ساخته و در مرکز دانلود می‌نشیند + یادداشت انتشار
 (چه چیزی عوض شده، آیا به `wrangler.toml` چیزی نیاز است یا نه).
5. شما فقط: باندل را بگیر → `node scripts/update-remote.mjs` → تأیید `/health`.

یعنی به‌روزرسانی = دانلود + یک فرمان.
