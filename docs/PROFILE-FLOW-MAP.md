# نقشهٔ کد و فلوی «پروندهٔ دانش‌آموز» — نسخهٔ ۱.۲۷.۴۹

> هدف: پایهٔ مشترک برای ۶ طرح ارتقای مستقل (ساب‌ایجنت‌ها) و مرجع پیاده‌سازی. همهٔ شاهدها با مسیر/خط واقعی کد. مکمل [REPORT-DESIGN.md](./REPORT-DESIGN.md) (گزارش‌ساز G1..G7) و [PRODUCT-STORY-CRITIQUE.fa.md](./PRODUCT-STORY-CRITIQUE.fa.md).
> سه محور خواست کارفرما: **تب‌ها** · **تاریخچهٔ فعالیت‌ها** · **گزارش‌های خروجی** + اصل «قسمت‌های مختلف پرونده در کنار هم معنی‌دار بشوند».

## ۱) ساختار نما — `public/assets/js/views/student-profile.js` (۱۴۳۳ خط، یک فایل)

```
renderStudentProfile(container, ctx)
├─ بار اول: فقط /api/students/:id (خط ۵۵) → اسکلت؛ بقیه در پس‌زمینه (Promise.all خط ۷۷)
├─ statusCard «کارت وضعیت» + buildCardCircles (خط ۱۲۱): دکمه‌های دایره‌ای
│    ویرایش · برچسب‌ها · هدف‌های شناختی · معلم‌ها · (تاریخچهٔ تحصیلی · حذف)
├─ docsQuickCard (کارت مدارک خودگردان — خط ۲۹۰)
├─ tabBar (۷ تب، خط ۲۶۶) + content
└─ قرارداد «بازسازی بی‌صدا» ۱.۲۰.۰: refreshCore/events/tags/focus بر اساس mutation
     → repaintChrome + rerenderTabIf([...]) — نقشهٔ دستی میوتِیشن‌ها (خطوط ۳۶۶-۳۷۳)
```

## ۲) تب‌های فعلی (renderer map خط ۲۲۵)

| کلید | عنوان | رندرر | محتوا |
|---|---|---|---|
| `info` | اطلاعات پایه | `renderInfoTab` (۳۹۶) | شناسنامه، مدرسه/کلاس/معلم، برچسب‌ها، وضعیت پرونده، هدف‌های شناختی |
| `clinical` | تفسیر بالینی | `clinical-insights.js` (فقط نقش بالینی) | روایت، پروتکل قضاوت، شاخه‌خوردن با مسیر پرونده |
| `timeline` | تاریخچه | `renderTimelineTab` (۴۹۲) | خط زمانی سرور-محور + ۹ فیلتر |
| `sessions` | جلسات | `renderSessionsTab` (۶۳۴) | شمار حضور/غیاب/انتظار + رویدادها و «ثبت گزارش» هر جلسه |
| `exercises` | تمرین‌ها | `exercise-send.js` | تخصیص/ارسال تمرین با بله |
| `games` | بازی‌ها | `renderGamesTabContent` (۳۸۱، import داینامیک) | تجویز/گزارش پارادایم‌ها (مدیر/درمانگر) |
| `comms` | ارتباطات | `renderCommsTab` (۷۰۹) | لینک بات، «ارسال گزارش به معلم مدرسه» (مودال ۹۶۷)، گزارش‌های ارسالی |

دسترسی‌ها: `canSeeClinical` / `canSeeGames` / `canManageTags`؛ دیپ‌لینک `#/student/:id?tab=` و فیلتر عمیق `?filter=followups`.

## ۳) تب تاریخچه — خط زمانی سرور-محور

- کلاینت (`renderTimelineTab` ۴۹۲): فیلترهای چیپی (`TIMELINE_FILTERS` خط ۳۵: همه/جلسات/یادداشت جلسه/رویدادها/پیگیری/کمیسیون/تمرین/پیام‌ها/پرونده)، صفحه‌سازی ۳۰تایی با دکمهٔ «بیشتر»، گارد نسل F2، حالت خالیِ راهنما.
- سرور: `src/application/student-timeline/` — تجمیع از **۹ جدول**: `audit_log` (ایجاد پرونده/برچسب/وضعیت/نیاز ویژه/مالک — اکشن‌های خط ۱۳۱)، `appointment_students`، `followups`، `waitlist`، `notifications`، `committee_items`، `exercise_assignments`، `case_events`؛ نرمال‌سازی به `{at, kind, title, subtitle, actor, ref}` + `meta.hasMore`.

## ۴) تب جلسات

شمارندهٔ حضور از `appointments[].myAttendance`؛ هر جلسه → رویدادهای `case_events` همان جلسه (`appointmentId`) + سلول «گزارش»: نمایش آخرین رویداد / ثبت گزارش جدید (`canCreateCaseEvents`)؛ یادداشت‌ها از timeline با `kinds=session_note` (خط ۸۳، سقف ۲۰۰).

## ۵) بارگیری داده — اولین ورود سنگین است

`Promise.all` خط ۷۷ با ~۱۰ فراخوانی: `/api/schools`، `appointments?limit=50`، `tags`×۲، `case-events?limit=200`، `timeline?kinds=session_note&limit=200`، `/api/staff`، `timeline?limit=30`، focus keys/labels. هر mutation فقط زیردرخت خودش را تازه می‌کند (خطوط ۳۵۶-۳۵۸ و نقشهٔ ۳۶۶-۳۷۳).

## ۶) بک‌اند مرتبط

- `src/domain/student-profile/`: service ۱۲۹۳ خط (CRUD، مدارس/معلم، وضعیت پرونده، نیاز ویژه، focus)، repository ۲۶۲، routes ۳۴۰، types ۲۶۴.
- `case-events` (رویداد/فرم‌ساز + `form-builder` + `survey-insights` + فرم عمومی خانواده/معلم)، `committee` روی گزارش‌های `reports.js`، `assessment-blocks`، `exercise-bank`، `games`، `followups`، `document-requests`، `tags`، `clearbook` (خط زمانی مرکز).
- گزارش‌ساز طراحی‌شده: `docs/REPORT-DESIGN.md` — قرارداد `ReportSection` + snapshot + کاتالوگ G1..G7؛ امروز **هیچ پیوندی بین پرونده و موتورهای گزارش نیست** (progress-report نمای جدا است).

## ۷) خروجی‌های گزارشِ امروز از خود پرونده

1. «ارسال گزارش به معلم مدرسه» (مودال متن آزاد → بات بله؛ ردپا در timeline به‌صورت notification).
2. «ثبت گزارش جلسه» در تب جلسات → `case_events` (فرم‌ساز).
3. چاپ جزیره‌ای در نماهای دیگر (`progress-report.js` A4، `finance`، `center-kpi`) — از پرونده نمی‌رسد.
4. یادداشت/رویدادها فقط داخل سامانه؛ **نسخهٔ قابل‌امضا/چاپ/اداره از پرونده وجود ندارد**.

## ۸) ضعف‌های مشهود (نقطهٔ شروع، حکم نهایی با هر طرح)

1. تب‌ها بدون «حکم» و عمق نابرابر: `info` پاتین‌فوقی، `games`/`comms` ابزاری — سلسله‌مراتب روایت ندارد.
2. تاریخچه رویداد-محور است نه روایت‌محور: بدون جمع‌بندی دوره، بدون «چی عوض شد نسبت به قبل»، بدون جست‌وجو.
3. پرونده = مصرف‌کنندهٔ داده؛ تولیدکنندهٔ گزارش نیست (پیوست‌ها جدا، امضا/مهر/نسخه ندارد).
4. اولین ورود ~۱۰ endpoint موازی؛ سقف‌های ۲۰۰/۵۰ عددی و بدون cursor.
5. یک فایل ۱۴۳۳ خطی با نقشهٔ دستی rerenderTabIf — ریسک رگرسیون در هر افزوده.
6. حالت‌های خالی راهنما خوب‌اند اما مسیر اقدام‌محور («چه چیزی از این پرونده معلق است؟») نمی‌دهند.
7. بازی‌ها/وکسلر/پرسشنامه‌ها (survey-insights) در تب‌های پرونده یکپارچه روایت نمی‌شوند.
8. مالی/مدارک ناقص (document-requests) در پرونده دیده می‌شوند اما در هیچ جمع‌بندی خروجی ظاهر نمی‌شوند.

## ۹) قواعد هر طرح باید رعایت کند

- قرارداد بازسازی بی‌صدا ۱.۲۰.۰ و گیت‌های مخزن (tsc/vitest/perf/font-floor/…).
- گیت کف فونت ۱۲px و tokens چاپ A4 موجود (موتور چاپ `progress-report.js`).
- RBAC موجود بدون نقش تازه (مدیر/منشی/درمانگر/معلم/خانواده) + audit append-only.
- با REPORT-DESIGN.md هم‌سو (نه دوباره‌تعریف): پرونده «منبع بخش‌های گزارش» می‌شود.
- توکن‌محور و حریم خانواده: تشخیص DSM/مالی در خروجی خانواده ممنوع.
- بدون placeholder: هر بخش طرح یا دادهٔ زنده دارد یا صادقانه «ندارم» می‌گوید.
