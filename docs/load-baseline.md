## ۲. محیط اندازه‌گیری — هشدار صادقانه

- ورکر **محلی** (`wrangler dev`، پورت ۸۷۸۷، workerd همین ماشین لینوکسی سندباکس، D1 محلی فایل‌محور).
- **این اعداد تأخیر لبهٔ کلادفلر را اندازه نمی‌گیرد.** تأخیر شبکه، توزیع isolate، کش لبه و سقف‌های واقعی حساب تولید اینجا وجود ندارند.
- کاربرد صحیح این اعداد: **مبنای مقایسهٔ رگرسیونی نسخه‌ها روی همین ماشین** (روی همان سخت‌افزار و دادهٔ مشابه) — نه عدد «سرعت تولید».
- اعداد «سطرهای خوانده/نوشته» در تحلیل ×۱۰ **برآورد تحلیلی از ساختار SQL** هستند نه شمارش D1 (wrangler dev متریک rows_read نمی‌دهد) — برچسب هر عدد در جدول‌ها صریح است.

## ۳. دادهٔ حجمی فقط-محلی (برای معنادارشدن خوانش سنگین)

`seed-dev.sql` تنها ۶ دانش‌آموز و صفر نوبت دارد؛ روی آن، runner با `--seed-only` دادهٔ حجمی deterministic ریخت (شناسه‌های ثابت + `INSERT OR IGNORE` → اجرای دوباره idempotent):

| جدول | شمار (پس از seed حجمی) |
|---|---|
| staff | ۴ |
| students | ۸۰۶ |
| appointments | ۳٬۰۰۰ (۷۵ روز × ۴۰ نوبت/روز؛ ۶۰ روز گذشته + ۱۵ روز آینده؛ ~۸٪ لغوشده) |
| appointment_students | ۳٬۶۰۰ |

حاشیهٔ عملیاتی: یک فراخوان واحد `wrangler d1 execute` با SQL کامل (~۱.۳MB) در workerd محلی segfault می‌دهد؛ runner همان SQL را در چانک‌های ~۵۵KB (۳۰۰ سطر) می‌فرستد — همین رفتار در کامنت کد ثبت شده است.

یادداشت‌های خوانش اعداد:

- **login p95 = ۹۷ms** عمدتاً PBKDF2 (۲۵هزار دور SHA-256 روی WebCrypto) + امضای JWT + نوشتن ردیف audit است — مسیر CPU-سنگین عمدی (هم‌زمان‌سازی زمان پاسخ) و نرمال.
- **reports** با پنجرهٔ ۳۰روزه و دادهٔ حجمی بالا پایدار است (تجمیع در SQL، بدون IN-list بزرگ) — p95 ۹۶ms.
- **dashboard/today** شامل سه COUNT کل جدول دانش‌آموزان (getDirectoryStats) + اسکن نوبت امروز + کشف تعارض است — p95 ۸۰ms.
- قناری «dashboard_summary_30d» عمداً پابرجاییِ باگ بخش ۵ را در هر اجرای آینده ثبت می‌کند: تا پیش از رفع، ۵۰۰ «انتظار» است و چک‌ها سبز؛ اگر روزی ۲۰۰ شود چک قرمز می‌شود تا این سند به‌روز شود. — **به‌روزرسانی ۱.۲۵.۷۲: این تلهپوایر شلیک شد** (رفع ف۵ واقعاً اعمال شده بود) و قناری به انتظار «۲۰۰ + بدنهٔ معتبر» چرخید؛ بخش ۴-الف.

## ۴-الف. پیوست ۱.۲۵.۷۲ — تلهپوایر شلیک شد: قناری به انتظار سالم چرخید

در چرخهٔ م۲ چرخهٔ تست/بنچمارک کارفرما، اجرای baseline روی ۱.۲۵.۷۱ قناری را قرمز گرفت (۲۱/۲۱ چک ناموفق) — دقیقاً مطابق طراحی بخش ۴: باگ در ۱.۲۵.۷۰ رفع شده بود اما قناری هنوز «۵۰۰» را انتظار می‌کشید. اقدام ۱.۲۵.۷۲:

- قناری `summary30dScenario` به دو چک «۲۰۰ + بدنهٔ JSON معتبر» چرخید — از این پس قرمزیِ قناری یعنی رگرسیون واقعی باگ، نه حالت سالم.
- پویش کامل همهٔ سازنده‌های IN-list در سورس (بدهی ف۶ ⑧) با دروازهٔ مشترک `@core/db/in-chunks` (تکه‌بندی ۹۰تایی + گارد IN خالی) بسته شد؛ گیت پویش دائمی `in-list-chunk-gate` هر سازندهٔ تازه را یا به دروازه می‌برد یا «IN-bounded» مستند می‌کند.

## ۵. یافتهٔ ظرفیت‌سنجی: سقف ۱۰۰ پارامتر بایند D1 — خلاصهٔ دورهٔ ۳۰روزه می‌شکند

مسیر `GET /api/dashboard/summary` → `appointments.list()` → پس از واکشی نوبت‌های بازه، `selectStudentsOfAppointments` (`src/domain/appointment-core/repository.ts`) همهٔ شناسه‌ها را در **یک IN-list** می‌بندد. سقف رسمی D1: «Maximum bound parameters per query = 100» (مستندات Limits کلادفلر). با دادهٔ حجمی محلی (۴۰ نوبت/روز):

| پنجرهٔ درخواست | نوبت‌های بازه | وضعیت پاسخ |
|---|---|---|
| ۱ روز | ۴۰ | ۲۰۰ OK (۱۷ms) |
| ۲ روز | ۸۰ | ۲۰۰ OK (۲۳ms) |
| ۳ روز | ۱۲۰ | **۵۰۰** — `D1_ERROR: too many SQL variables` |
| ۳۰ روز | ۱٬۲۰۰ | **۵۰۰** برای ۱۰۰٪ درخواست‌ها (۲۱/۲۱ در سناریوی قناری) |

معنی عملی: این **سقف حجم-داده است نه ترافیک** — هر مرکزی با میانگین ≳۳٫۴ جلسه در روز همان ماه، خلاصهٔ دوره را با ۵۰۰ می‌بندد؛ این کاملاً داخل دامنهٔ کاربردِ امروزِ محصول است، نه سناریوی فرضی ×۱۰. گزارش‌ها و تابلوی امروز آسیب‌نپذیرند (تجمیع در SQL / IN کوچک). رفع پیشنهادی (مایلستون بعدی، خارج از دامنهٔ این سند): چانک‌کردن IN-list (به‌ازای هر ≤۹۰ شناسه) یا تجمیع پیوند نوبت‌ـ‌دانش‌آموز در یک query با join بازه‌ای. تا رفع، عدد عملکردی «خلاصهٔ دوره» در این سند روی پنجرهٔ کارای ۲روزه ثبت شده است.

### ۶-۱. آمیزهٔ درخواست روزانه — برچسب صادقانه: «برآورد»

بار اندازه‌گیری‌شده‌ی بالا، نرخ لحظه‌ای را می‌سنجد؛ برای مقایسه با سقف «روزانه» باید آمیزهٔ مصرف یک روز کاری را فرض کرد. فرض‌ها (منطقی برای یک مرکز با ~۱۵ کاربر و ~۴۰ جلسه/روز؛ بعداً با گزارش رشد جدول‌ها و تله‌متری باید جای‌گزین عدد واقعی شود):

| مسیر | ×۱ برآورد/روز | سطر خوانده/درخواست (برآورد از SQL در حجم فعلی) | سطر نوشته/درخواست |
|---|---|---|---|
| ورود موفق | ۴۰ | ~۲۲ (staff+throttle+audit-INSERT×1) | ۱-۲ |
| تابلوی امروز | ۲۰۰ | ~۹۰۰ (۴۰ نوبت + ۳×COUNT students≈۸۱۰ + staff + تعارض) | ۰ |
| خلاصهٔ دوره (پس از رفع IN) | ۳۰ | ~۲٬۶۵۰ (۱٬۲۰۰ نوبت + ۱٬۴۴۰ پیوند + staff) | ۰ |
| گزارش | ۱۵ | ~۵٬۰۰۰ (تجمیع‌های چندجدولی روی students/appointments) | ۰ |
| خوانش‌های سبک دیگر (فهرست‌ها/جست‌وجو) | ۴۰۰ | ~۱۰۰ | ۰ |
| نوشتن‌ها (نوبت/حضور/یادداشت/…) + audit هر کدام | ۱۲۰ | ~۵۰ (اعتبارسنجی‌ها) | ۲-۳ (شامل audit_log) |

### ۶-۲. ریاضی سقف‌ها

**Rows read — روزانه:**

| سناریو | محاسبه | جمع | نسبت به سقف ۵M/روز |
|---|---|---|---|
| ×۱ (امروز، برآورد) | ۴۰×۲۲ + ۲۰۰×۹۰۰ + ۳۰×۲٬۶۵۰ + ۱۵×۵٬۰۰۰ + ۴۰۰×۱۰۰ + ۱۲۰×۵۰ | ≈ **۳۵۲ هزار/روز** | ~۷٪ — امن |
| ×۱۰ ترافیک، همان حجم داده | همهٔ سطرهای جدول بالا ×۱۰ | ≈ **۳٫۵ میلیون/روز** | **~۷۰٪ — زنگ خطر** |
| ×۱۰ ترافیک + ×۱۰ رشد داده (۸هزار دانش‌آموز) | COUNT(*)های full-scan با جدول ×۱۰ بزرگ‌تر می‌شوند → «سطر خوانده/درخواست» هم ×۱۰ (تابلو ~۹٬۰۰۰؛ خلاصه/گزارش ~۲۶-۵۰هزار) | ≈ **۱۸ میلیون+/روز** | **~۳٫۶× عبور از سقف — کوئری‌ها خطا می‌دهند** |

نکتهٔ کلیدی: خواندن سطرها در D1 با **ضربِ ترافیک در حجم جدول** رشد می‌کند (هر COUNT(*) همهٔ جدول را می‌خواند) — یعنی ×۱۰ ترافیک + ×۱۰ داده ≈ ×۱۰۰ خواندن، نه ×۱۰. سه COUNT کل جدول students در تابلوی امروز و تجمیع‌های گزارش، دو مسیر غالب‌اند.

**Rows written — روزانه:**

| سناریو | محاسبه | جمع | نسبت به سقف ۱۰۰k/روز |
|---|---|---|---|
| ×۱ | ۱۲۰ نوشتن ×۲-۳ + ۴۰ ورود ×۱-۲ + audit | ≈ **۰٫۵ هزار/روز** | <۱٪ |
| ×۱۰ | ×۱۰ | ≈ **۵ هزار/روز** | ~۵٪ — امن |
| ×۱۰ با رشد | ×۱۰ | ≈ **۵ هزار/روز** (نوشتن با حجم جدول رشد خطی ندارد) | امن |

**Storage:** رشد ≈ ۱۴٫۶هزار نوبت/سال در ×۱ (~۳MB/سال با ردیف‌های پیوند) — در ×۱۰ هم چند ده MB در سال؛ سقف ۵۰۰MB دیتابیس/۵GB حساب سال‌ها فاصله دارد.

### ۶-۳. نتیجهٔ ×۱۰ (دو جمله)

۱. گلوگاه اول و تنها خطر واقعی در ×۱۰، **«سطرهای خوانده» پلن Free** است: با رشد هم‌زمان ترافیک و داده، COUNT(*)های full-scan (تابلوی امروز: ۳×COUNT students؛ تجمیع‌های گزارش) روزانه را از ~۳٫۵M به بالای سقف ۵M می‌برند و از ۲۰۲۶-۰۹ کوئری‌ها سخت خطا می‌دهند — پادزهرهای مشخص: شمارنده‌های نگه‌داشته‌شده/کش کوتاه‌عمر برای stats، ایندکس‌پوششِ تجمیع‌ها، یا ارتقای Workers Paid (۲۵ میلیارد سطر/ماه شامل است ≈ ۸۳۰M/روز).
۲. دومین سقفِ مستقل از ترافیک، **۱۰۰ پارامتر بایند D1** است که امروز همین حالا با پنجرهٔ ≥۳روزهٔ ۴۰جلسه‌ای می‌شکند (بخش ۵) و در مرکزی ×۱۰ بزرگ‌تر، هر روز می‌شکند — رفع چانک‌شدهٔ IN-list باید مایلستون بعدی باشد.

## ۷. اجرای مجدد (runbook کوتاه)

```bash
# یک‌بار، با سرور خاموش:
npm run load:baseline -- --seed-only     # ریختن دادهٔ حجمی فقط-محلی (idempotent)
npm run migrate:local && npm run seed:local  # مایگریشن + دادهٔ پایهٔ dev

# ترمینال دیگر:
npm run dev                              # wrangler dev روی 8787

# اجرای بار (در ترمینال سوم یا بعد از آماده‌باش):
npm run load:baseline                    # جدول فارسی + JSON مرجع در /tmp/load-baseline
```

پرچم‌های runner: `--base-url` · `--out` · `--k6` · `--user/--pass` · `--quiet`. باینری k6 اگر در PATH نباشد از `/tmp/k6-dist/k6` هم پیدا می‌شود؛ نصب = بازکردن tarball استاتیک از GitHub Releases (بدون pipe-to-shell).

| برچسب | معنی در این سند |
|---|---|
| اندازه‌گیری‌شده | خروجی واقعی k6/سرور در همین اجرا |
| برآورد | محاسبهٔ تحلیلی از ساختار SQL و فرض مصرف — باید با تله‌متری/گزارش رشد جای‌گزین عدد واقعی شود |
