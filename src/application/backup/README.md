# پشتیبان‌گیری و بازیابی (m179)

این ماژول مکانیک «گرفتن نسخهٔ ذخیره از داده‌ها» و «برگرداندن فایل پشتیبان داخل پایگاه داده» را داخل خود سامانه فراهم می‌کند — بدون نیاز به ابزار بیرونی، فقط با دسترسی مدیر مرکز.

## مسیرها (همه فقط نقش manager؛ ناظر اداره به‌طور خودکار مسدود است)

| مسیر | کار |
|------|-----|
| `GET /api/backup/status` | فهرست جدول‌ها + تعداد ردیف‌ها + ۵ رویداد اخیر پشتیبان از `audit_log` |
| `GET /api/backup/export?include_files=1` | دانلود فایل پشتیبان (استریم). بدون `include_files` جدول سنگین `exercise_file_chunks` کنار گذاشته می‌شود |
| `POST /api/backup/inspect` | بررسی فایل پشتیبان **بدون هیچ نوشتنی** — اعتبارسنجی قالب + هم‌خوانی اسکیما + خلاصهٔ جدول‌ها |
| `POST /api/backup/restore` | بازیابی جایگزینی‌کل؛ بدنه `{ backup, confirm: true }` — بدون `confirm` رد می‌شود |

## قالب فایل پشتیبان — `gh-backup` نسخهٔ ۱

```json
{
  "format": "gh-backup",
  "format_version": 1,
  "app_version": "1.00.54",
  "milestone": "m179",
  "created_at": "2026-10-23T15:00:00.000Z",
  "include_files": false,
  "excluded_tables": ["exercise_file_chunks"],
  "tables": { "students": { "row_count": 120, "rows": [ … ] } }
}
```

- همهٔ جدول‌های `sqlite_master` به‌جز `sqlite_%` در فایل می‌آیند؛ `schema_migrations` فقط اطلاعاتی است و در بازیابی دست نمی‌خورد.
- مقادیر BLOB به base64 تبدیل می‌شوند (در اسکیمای فعلی عملاً رشتهٔ base64 ذخیره می‌شود).

## مکانیک بازیابی (قلب سیستم — بازنویسی m181)

1. **اعتبارسنجی**: قالب + برابری مجموعهٔ جدول‌های فایل با پایگاه فعلی (غیر از `schema_migrations`/`d1_migrations` و جدول‌های `excluded_tables`). هر تفاوت = رد کل عملیات با پیام روشن. + **پیش‌اعتبارسنجی ستون‌های الزامی**: ستون‌های «NOT NULL بدون پیش‌فرض» باید در همهٔ ردیف‌های فایل حاضر باشند وگرنه عملیات قبل از هر نوشتنی رد می‌شود.
2. **فاز ۱ — خالی‌کردن کامل**: همهٔ جدول‌های هدف در **یک batch واحد** (با `PRAGMA defer_foreign_keys = ON`) خالی می‌شوند. چون تا پایان همین تراکنش همه‌چیز خالی می‌شود، هیچ ردیف کهنی نمی‌ماند که به ردیف حذف‌شدهٔ جدولی دیگر ارجاع بدهد. *(این همان باگ پروداکشن m180 بود: DELETE+INSERT جداگانهٔ هر جدول باعث می‌شد فرزندان قدیمی به درجِ چانک بعدیِ والد برخورد کنند و «FOREIGN KEY constraint failed» بگیریم — در دادهٔ واقعی ۱۰۰٪ شکست می‌خورد.)*
3. **فاز ۲ — درج توپولوژیک**: از `PRAGMA foreign_key_list` هر جدول، وابستگی والد→فرزند لایه‌بندی می‌شود (Kahn) و درج در ترتیب والد→فرزند انجام می‌گیرد؛ چون پایگاه الان خالی است، chunking هر جدول بی‌خطر است. چرخهٔ FK → همهٔ جدول‌های چرخه در **یک batch** با تعویق FK درج می‌شوند. جدول خود-ارجاع → همهٔ ردیف‌ها در یک batch.
4. **chunking تطبیقی**: درج تک‌ردیفی (سقف ۱۰۰ پارامتر D1)؛ هر batch حداکثر ۳۰ دستور یا ~۲MB پارامتر.
5. **پروجکشن ستونی**: ستون‌های فایل که در اسکیمای فعلی نیستند نادیده گرفته و در گزارش هشدار می‌شوند؛ ستون‌های فعلیِ غایب در فایل NULL درج می‌شوند.
6. **جدول‌های سیستمی**: `schema_migrations` و `d1_migrations` در بازیابی هرگز دست نمی‌خورند — بازگرداندن نسخهٔ کهنهٔ `d1_migrations` باعث می‌شد `d1 migrations apply` بعدی مهاجرت‌های اعمال‌شده را دوباره بزند.
7. **گزارش + دفتر ثبت**: تعداد ردیف بازگردانده‌شدهٔ هر جدول + مدت + هشدارها؛ رویداد `backup.restore` در `audit_log`.

## خروجی استریمی (بازنویسی m181)

- به‌جای پمپ‌کردن همه‌چیز در `start()` (که صف استریم و حافظهٔ Worker را با فایل ~۱۰۰ مگابایتی پر می‌کرد)، خروجی **pull-based** است: هر `pull` فقط یک گام (یک ردیف/یک بخش) از مولد جلو می‌رود و صف همیشه کوچک می‌ماند.
- ردیف‌های `exercise_file_chunks` (تا ~۲ مگابایت هرکدام) با صفحهٔ ۴تایی خوانده می‌شوند تا یک کوئری سنگین (~۱۲۰MB) شکل نگیرد؛ بقیهٔ جدول‌ها صفحهٔ ۴۰۰تایی.

### چرا بازیابی سبک (بدون فایل‌ها) امن است؟
جدول `exercise_file_chunks` هیچ کلید خارجی ندارد؛ در بازیابی سبک دست نمی‌خورد و بایت فایل‌های پیوستی سر جایشان می‌مانند. `CASCADE`ها هم بی‌خطرند چون والد همیشه قبل از فرزند بازسازی می‌شود و ردیف‌ها با همان id برمی‌گردند.

### محدودیت صادقانه
بازیابی «کل پایگاه» در چند batch انجام می‌شود؛ اگر وسط مسیر خطای زیرساختی رخ دهد، وضعیت نیمه‌بازگردانی می‌ماند. به همین دلیل رابط کاربری **گام ۱ را گرفتن «فایل اطمینان» از وضعیت فعلی اجباری می‌کند** و D1 خودش Time Travel (۳۰ روز بازیابی نقطه‌ای) دارد.

## m180 — ارسال پشتیبان به آیدی بله (مقصد انتخابی)

- **مقصدها**: آرایهٔ `{id, label, chat_id, active}` در `settings` با کلید `backup_destinations` (حداکثر ۱۰، آیدی عددی بله با `BACKUP_CHAT_ID_RE`، بدون تکرار). ارقام فارسی/عربی آیدی خودکار به لاتین تبدیل می‌شوند (m181) — خطای رایج کاربرانِ کیبورد فارسی. ذخیره کامل = `PUT /api/backup/delivery` (مقصدها + `backup_auto_send` با هم).
- **ارسال**: `POST /api/backup/send {destinations: [id], include_files?}` — پاکت `gh-backup` یک‌بار در حافظه ساخته (`collectExport`، سقف `BACKUP_MAX_SEND_BYTES` = ۴۸MB) و برای هر مقصد انتخابیِ فعال با `sendBaleDocument` (multipart → `tapi.bale.ai/bot<token>/sendDocument`) فرستاده می‌شود؛ خطای یک مقصد بقیه را متوقف نمی‌کند و گزارش رودررویی + `audit backup.send` برمی‌گردد.
- **پشتیبان خودکار شبانه**: کلید `backup_auto_send` = `{enabled, destination_ids, include_files}`؛ در cron دیجست (`0 4 * * *`) بعد از حلقهٔ اعلان‌ها، `runScheduledAutoSend()` فقط اگر enabled + مقصد فعالِ انتخاب‌شده وجود داشته باشد اجرا می‌شود (`audit backup.auto_send`).
- **sender تزریقی**: `createBackupService({sender})` / `AppDeps.backupDocumentSender` برای تست‌ها؛ در پروداکشن از `baleToken` ساخته می‌شود. `bot_ready` در `GET /api/backup/delivery` وضعیت توکن را می‌گوید.
