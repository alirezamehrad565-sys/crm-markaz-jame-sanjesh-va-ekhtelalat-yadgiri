# پشتیبان‌گیری و بازیابی (m179)

این ماژول مکانیک «گرفتن نسخهٔ ذخیره از داده‌ها» و «برگرداندن فایل پشتیبان داخل پایگاه داده» را داخل خود سامانه فراهم می‌کند — بدون نیاز به ابزار بیرونی، فقط با دسترسی مدیر مرکز.

## مسیرها (همه فقط نقش manager؛ ناظر اداره به‌طور خودکار مسدود است)

| مسیر | کار |
|------|-----|
| `GET /api/backup/status` | فهرست جدول‌ها + تعداد ردیف‌ها + ۵ رویداد اخیر پشتیبان از `audit_log` |
| `GET /api/backup/export?include_files=1` | دانلود فایل پشتیبان (استریم). بدون `include_files` جدول سنگین `exercise_file_chunks` کنار گذاشته می‌شود |
| `POST /api/backup/inspect` | بررسی فایل پشتیبان **بدون هیچ نوشتنی** — اعتبارسنجی قالب + هم‌خوانی اسکیما + خلاصهٔ جدول‌ها |
| `POST /api/backup/restore` | بازیابی جایگزینی‌کل؛ بدنه `{ backup, confirm: true }` — بدون `confirm` رد می‌شود |

## قالب فایل پشتیبان — `gh-backup` نسخهٔ ۱

```json
{
  "format": "gh-backup",
  "format_version": 1,
  "app_version": "1.00.54",
  "milestone": "m179",
  "created_at": "2026-10-23T15:00:00.000Z",
  "include_files": false,
  "excluded_tables": ["exercise_file_chunks"],
  "tables": { "students": { "row_count": 120, "rows": [ … ] } }
}
```

- همهٔ جدول‌های `sqlite_master` به‌جز `sqlite_%` در فایل می‌آیند؛ `schema_migrations` فقط اطلاعاتی است و در بازیابی دست نمی‌خورد.
- مقادیر BLOB به base64 تبدیل می‌شوند (در اسکیمای فعلی عملاً رشتهٔ base64 ذخیره می‌شود).

## مکانیک بازیابی (قلب سیستم)

1. **اعتبارسنجی**: قالب + برابری مجموعهٔ جدول‌های فایل با پایگاه فعلی (غیر از `schema_migrations` و جدول‌های `excluded_tables`). هر تفاوت = رد کل عملیات با پیام روشن.
2. **ترتیب توپولوژیک**: از `PRAGMA foreign_key_list` هر جدول، وابستگی والد→فرزند ساخته و لایه‌بندی می‌شود (الگوریتم Kahn). چرخهٔ FK → همهٔ جدول‌های چرخه در **یک batch** بازیابی می‌شوند.
3. **اتمیک بودن هر جدول**: برای هر جدول، `DELETE` + `INSERT`ها در همان batch می‌آیند؛ دستور اول هر batch `PRAGMA defer_foreign_keys = ON` است تا ارجاع‌های درون-تراکنش و ردیف‌های خود-ارجاع در لحظهٔ commit بررسی شوند. نتیجه: هر جدول یا کامل برمی‌گردد یا دست نمی‌خورد.
4. **chunking تطبیقی**: درج تک‌ردیفی (سقف ۱۰۰ پارامتر D1)؛ هر batch حداکثر ۳۰ دستور یا ~۲MB پارامتر. جدول خود-ارجاع → همهٔ ردیف‌ها در یک batch.
5. **پروجکشن ستونی**: ستون‌های فایل که در اسکیمای فعلی نیستند نادیده گرفته و در گزارش هشدار می‌شوند؛ ستون‌های فعلیِ غایب در فایل NULL درج می‌شوند.
6. **گزارش + دفتر ثبت**: تعداد ردیف بازگردانده‌شدهٔ هر جدول + مدت + هشدارها؛ رویداد `backup.restore` در `audit_log`.

### چرا بازیابی سبک (بدون فایل‌ها) امن است؟
جدول `exercise_file_chunks` هیچ کلید خارجی ندارد؛ در بازیابی سبک دست نمی‌خورد و بایت فایل‌های پیوستی سر جایشان می‌مانند. `CASCADE`ها هم بی‌خطرند چون والد همیشه قبل از فرزند بازسازی می‌شود و ردیف‌ها با همان id برمی‌گردند.

### محدودیت صادقانه
بازیابی «کل پایگاه» در چند batch انجام می‌شود؛ اگر وسط مسیر خطای زیرساختی رخ دهد، وضعیت نیمه‌بازگردانی می‌ماند. به همین دلیل رابط کاربری **گام ۱ را گرفتن «فایل اطمینان» از وضعیت فعلی اجباری می‌کند** و D1 خودش Time Travel (۳۰ روز بازیابی نقطه‌ای) دارد.

## لایهٔ CLI عملیات (مکمل)

| فرمان | کار |
|-------|-----|
| `npm run backup:remote` | خروجی SQL کامل (اسکیما + داده) از D1 پروداکشن در `backups/backup-*.sql` |
| `npx wrangler d1 execute center-system-db --remote --file=backups/<فایل>.sql` | بازیابی کامل SQL (برای فاجعه/پایگاه تازه) — فقط با هماهنگی |

سند کامل عملیات: `docs/BACKUP.md`.
